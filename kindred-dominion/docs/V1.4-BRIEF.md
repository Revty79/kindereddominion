# Kindred Dominion — V1.4: Complete Player Experience and Release Foundation

## Owner directive

Kindred Dominion must now transition from a development-oriented prototype into a functional, persistent game that the owner can test from the perspective of an ordinary player.

The owner wants to register an account, acquire cards, manage a personal collection, create decks, choose cards to take into battle, play complete matches, and retain progress between sessions.

The owner also requires a privileged development account with access to Developer Studio.

This assignment is an implementation assignment, not another isolated visual demonstration or planning exercise.

## 1. Audit and preserve existing development

Before implementation:

- Review the latest repository commits.
- Review all existing approved game design documents and development assignments.
- Audit the current PostgreSQL implementation, migrations, authentication infrastructure, player builds, publishing pipeline and gameplay engine.
- Identify features that already exist and reuse them.
- Preserve existing owner-approved mechanics.
- Preserve all permanent collectible card IDs.
- Preserve all existing artwork masters and revisioned runtime assets.
- Preserve the existing Developer Studio functionality.

Do not replace functioning systems simply because this assignment introduces a broader player experience.

Do not destroy existing database records or reset existing environments.

## 2. Approved card presentation — production integration

The owner approves the artwork-first, full-bleed card presentation demonstrated in the isolated visual study.

Integrate that approved presentation into the actual game.

The artwork itself must be the entire card face, with dynamically generated information overlays.

Use the same reusable renderer throughout:

- Card catalog.
- Personal collection.
- Deck builder.
- Opening hand.
- Mulligan selection.
- Player hand.
- Battlefield.
- Card inspection.
- Pack opening.
- Developer Studio.

Cards must appear as actual portrait cards placed onto battlefield tiles.

Maintain clear visibility of tile ownership, placement tokens, fortifications, effective power, row scores, targeting and legal placement.

Do not change the approved visual direction or return to thumbnail-based information panels.

Provide appropriately scaled card presentation and enlarged inspection.

Keep existing individual artwork acceptance exceptions separate from approval of the card renderer.

## 3. Main player application

Create a polished, game-oriented main application.

Ordinary players should not be greeted by a development dashboard, technical reports, testing controls or Developer Studio.

Provide clear navigation to:

- Main menu.
- Play.
- My Collection.
- Deck Builder.
- Card Catalog.
- Card Packs, using existing approved acquisition systems.
- Profile and statistics.
- Match history.
- Settings.
- Login, registration and logout as appropriate.

Only expose features that are actually functional.

Do not implement decorative buttons that lead to dead ends.

Use the existing Kindred Dominion visual identity and approved artwork.

The interface should feel like a cohesive collectible tactical card game.

## 4. Account registration and authentication

Implement or complete functional player authentication using the existing PostgreSQL infrastructure.

Required functionality:

- New account registration.
- Unique usernames.
- Valid email addresses.
- Secure password hashing.
- Login.
- Logout.
- Persistent authenticated sessions.
- Account profile.
- Password changes.
- Secure account recovery where supported by the environment.

If email delivery is not configured for local testing, clearly document the limitation and provide a secure development-only recovery testing procedure. Never pretend production email delivery is operational.

Implement appropriate security measures:

- Server-side authentication and authorization.
- Secure session handling.
- Appropriate cookie protections.
- CSRF protection where applicable.
- Authentication rate limiting.
- Input validation.
- Database uniqueness constraints.
- Prevention of unauthorized access to other accounts.

Never store plaintext passwords.

Never expose secrets through frontend code or repository commits.

## 5. Owner and Developer Studio access

The owner must have a privileged account that can access Developer Studio while also participating in the ordinary player experience.

Provide at minimum:

- Standard player permissions.
- Developer Studio permissions.
- Owner/administrator permissions.

Reuse any existing permission architecture where suitable.

Provide a secure, documented method for granting the owner's registered account the necessary permissions.

Do not automatically grant development privileges to the first registered account.

Do not hardcode privileged account passwords.

The owner must be able to:

- Register and use an ordinary player account.
- Use an authorized development account or an explicitly authorized privileged player account.
- Access Developer Studio through restricted navigation.
- Return to normal gameplay.
- Create, edit, test and publish cards using existing tools.
- Test unpublished cards in an isolated sandbox.

All privileged operations must be authorized on the server, not merely hidden in the interface.

## 6. PostgreSQL persistence

Use PostgreSQL as the authoritative persistent source for actual player accounts and player-owned game data.

Persist applicable data including:

- Player account and profile.
- Permissions.
- Owned cards and quantities.
- Saved decks.
- Active or preferred deck.
- Match history.
- Wins, losses and draws.
- Acquired rewards.
- Player progression supported by approved mechanics.
- Acquisition and reward transaction history.

Reuse existing tables, migrations and infrastructure where appropriate.

Create necessary migrations without destructively replacing existing data.

Browser storage may retain harmless preferences or temporary interface state but must not be authoritative for player ownership, rewards, permissions or competitive results.

Verify persistence after browser refresh, logout, login and application restart.

## 7. Published Card Catalog

Provide an accessible catalog containing all published founding cards.

The founding collection consists of 150 cards:

- Nature: N001–N030.
- Mythical: M001–M030.
- Arcane: A001–A030.
- Undead: U001–U030.
- Constructs: C001–C030.

Players must be able to browse, search, filter, sort and inspect the published catalog.

Include actual card definitions, artwork, influence diagrams, abilities and evolution requirements.

Clearly distinguish owned cards from unowned cards where applicable.

The public catalog is not the player's personal collection.

Unpublished development cards must not appear in the ordinary player catalog.

## 8. New-player onboarding and starter collections

New accounts must receive an appropriate starting collection using the existing approved acquisition and starter-deck rules.

Allow the player to make any starter choices already supported by our approved design.

Do not automatically give ordinary players every card simply for development convenience.

Do not invent a finalized starter economy if one has not been approved.

If an essential starter or acquisition rule is missing, identify the gap and provide an explicitly labeled, configurable local-testing default. Preserve the ability to replace that default without rewriting the account or collection systems.

Ensure starter grants are persistent, auditable and cannot be repeatedly claimed through refreshing, logging out or repeating onboarding.

A newly registered player must have a legal path to their first match.

## 9. Personal card collection

Implement the actual player-owned collection experience.

Players must be able to:

- Browse owned cards.
- View owned quantities.
- Filter by Kindred.
- Filter by card type, placement requirements and applicable attributes.
- Search by name or permanent card number.
- Inspect cards at full size.
- Identify cards not yet owned.
- View applicable acquisition information.

Card ownership must persist in PostgreSQL.

Prevent unauthorized collection modifications.

Support multiple owned copies of a card while maintaining the distinction between collection ownership and deck copy limits.

## 10. Deck creation and management

The player must be able to build their own decks rather than being limited to predefined demonstration decks.

Implement:

- Create a deck.
- Name and rename decks.
- Add and remove cards.
- Adjust card quantities.
- Save decks.
- Edit existing decks.
- Duplicate decks.
- Delete decks.
- Select a deck for battle.
- View deck legality and composition.

Use the approved deck size, copy limits, Kindred rules and game-mode restrictions.

Deck validation must use the player's actual owned collection.

Enforce all applicable legality rules on the server before a match begins.

Allow incomplete decks to be saved as drafts where practical, but prevent illegal decks from entering ordinary matches.

Do not alter approved deck rules to simplify implementation.

## 11. Complete match experience

Implement a complete normal player flow using the existing gameplay engine:

1. Log in.
2. Choose Play.
3. Choose an available game mode.
4. Choose an available opponent.
5. Select a saved legal deck.
6. Review match settings.
7. Begin the match.
8. Review the opening hand.
9. Complete the approved mulligan process.
10. Play the match using existing gameplay rules.
11. Reach a legitimate conclusion.
12. View match results.
13. Return to the main menu or begin another match.

Use the actual approved card renderer throughout gameplay.

Preserve all approved mechanics, including:

- Territory ownership.
- Placement tokens.
- Fortifications.
- Territory expansion and capture.
- Reinforcement.
- Overthrow.
- Destruction.
- Evolution.
- Replacement.
- Special abilities.
- Effective and printed power.
- Scoring variants.
- Passing and endgame rules.
- Universal anti-loop safeguards.

Provide the existing computer opponents through the normal player interface.

Do not require Developer Studio or access to development fixtures to start a match.

## 12. Server-authoritative gameplay and rewards

Ordinary player matches must be structured around trustworthy server-side validation.

The player must not be able to manipulate results, grant themselves cards, bypass deck restrictions or award themselves progression through browser requests.

Reuse the existing deterministic game engine.

Validate applicable:

- Player identity.
- Match participation.
- Deck ownership and legality.
- Turn ownership.
- Card placement.
- Targets.
- Gameplay actions.
- Match completion.
- Rewards.

Match rewards and other grants must be protected against duplication.

Do not award ordinary progression for sandbox matches.

This architecture must remain compatible with future multiplayer implementation.

## 13. Card acquisition and rewards

Expose existing approved card acquisition systems through the ordinary player application.

Where already implemented and approved, support:

- Starter cards.
- Earned card packs.
- Pack opening.
- Reward cards.
- Duplicate card quantities.
- Collection updates.

Use actual persistent ownership records.

Do not implement real-money transactions during this assignment.

Do not independently finalize pack pricing, rarity probabilities, currency systems or monetization policies that have not been approved.

Any temporary testing acquisition defaults must be explicitly identified, configurable, auditable and isolated from production economy decisions.

## 14. Player profile and match history

Provide a functional player profile that displays applicable real data:

- Username.
- Account creation information.
- Owned collection size.
- Completed decks.
- Total matches.
- Wins.
- Losses.
- Draws.
- Recent match history.
- Existing approved progression information.

Do not display invented statistics or simulated accomplishments as genuine player records.

## 15. Developer Studio and isolated testing

Preserve Developer Studio as a restricted development environment.

It must continue to support existing functionality for:

- Card creation.
- Artwork upload.
- Card definition editing.
- Territory influence configuration.
- Ability configuration.
- Live card previews.
- Validation.
- Publishing.
- Development testing.

Continue the artwork-first architecture.

Creating a new card should normally require uploading an illustration and configuring its gameplay definition, not manually designing a new card face.

Maintain the separation between:

- Original artwork.
- Card definitions.
- Reusable card renderer.
- Gameplay engine.
- Dynamic gameplay state.

Developer sandbox operations must not contaminate ordinary player collections, competitive statistics or progression.

Do not require normal players to interact with development tools.

## 16. Release-oriented build and deployment

Use the existing release-oriented player build and deployment infrastructure.

The owner wants to test the real game application, not a development-only prototype page.

Provide a reproducible local launch procedure that includes the required application services and PostgreSQL connection.

Verify that:

- The release-oriented application can be built.
- Registration and authentication function in the intended test environment.
- The player application loads without development-only assets or fixtures.
- Published artwork loads correctly.
- Normal players cannot access privileged development functionality.
- Authorized development accounts can access Developer Studio through an appropriate protected application surface.
- Restarting the application does not erase player data.

If the existing player build intentionally excludes Developer Studio, preserve that security boundary and provide an appropriate authenticated development application or protected administrative entry point using the same authorized account infrastructure.

Do not expose development tools or secrets by weakening the player build.

Preserve existing Docker and future Ubuntu deployment compatibility. Do not perform an unauthorized deployment to the owner's home server.

## 17. Actual end-to-end acceptance testing

This assignment is not complete merely because automated unit tests pass or individual interface components render correctly.

Launch the actual intended game application and perform the following acceptance scenario using a newly registered test account and the actual PostgreSQL-backed environment.

### Ordinary player acceptance scenario

- Register a new account.
- Log in.
- Complete onboarding.
- Receive the applicable starter collection.
- Browse the published card catalog.
- Browse the personal collection.
- Create a custom deck.
- Save the deck.
- Log out.
- Log back in.
- Confirm collection and deck persistence.
- Select the custom deck.
- Begin a normal match against a computer opponent.
- Complete the match.
- View the match result.
- Verify persistent match history.
- Acquire cards through an available approved or explicitly designated testing acquisition path.
- Verify the updated collection.
- Restart the application.
- Confirm that account, collection, decks and match records persist.

### Developer acceptance scenario

- Authenticate with a properly authorized development account.
- Access Developer Studio.
- Verify existing card creation and editing functionality.
- Verify live artwork-first card previews.
- Test a card in an isolated sandbox.
- Confirm that sandbox activity does not modify ordinary player progression.
- Return to the normal player experience or its designated application entry point.

### Security acceptance scenario

- Verify that an ordinary player cannot access Developer Studio operations.
- Verify that one account cannot modify another account's collection or decks.
- Verify that unowned cards cannot be used in normal player decks.
- Verify that illegal gameplay actions are rejected.
- Verify that rewards cannot be claimed repeatedly.
- Verify that secrets and privileged credentials are not included in client assets or Git.
