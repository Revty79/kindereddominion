It includes target verification, a private backup, additive migrations and content synchronization. No reset is needed. The current schema has 21 migrations. ## Inspect an inactive proposal

1. Sign in with an administrator account. Open **Administration → Starter collections**.
2. Choose **Create draft from latest DEV proposal**. Keep both grant activation boxes unchecked and hosted review empty.
3. Review each Kindred's ten additional copies, fifteen-card recommended deck and two alternatives. The configuration document supports changing the number of additional identities; their quantities must total ten. Use a new recipe version when changing published definitions.
4. Choose **Validate and save draft**, enter a publication reason, then **Publish reviewed draft**. Invalid ownership, deck limits, missing evolution predecessors, insufficient opening slots, retired additional identities and incompatible published competitive formats prevent publication.
5. Choose **Refresh starter records**, search for an existing player, select that account, then **Preview exact starter upgrade**. Inspect the ten additions and the current/after quantities. The disabled proposal cannot apply grants.
6. Inspect the original-Kindred review queue. Missing or conflicting evidence must be resolved through an authorized investigation; the application never guesses the original Kindred. This milestone adds no automatic identity-correction tool.

The default recipe is `founding-40-proposal-v1`. The reviewed definitions are identified by digest:

```text
6420f2e5ee092fed9e09f7d7efcd81cfd9608b3e24fea8e5b4be2e0e9023cee3
```

Changing definitions changes the digest. This value identifies content; it is not approval from the owner.

## Exercise the proposal in DEV

1. Back up the verified DEV database. Use representative test accounts; keep existing custom decks for comparison.
2. Create a draft from current settings. Enable **forty-copy grants for new selections** and, if testing backfill, **reviewed existing-account upgrades**. Save, review and publish with a DEV-specific reason. Hosted approval fields remain empty for isolated DEV testing.
3. Create a new account for each founding Kindred. Confirm 30 unique identities, 40 total playable copies and the appropriate legal 15-card recommended deck. Only the original 30 identities count toward first-copy collection completion.
4. Modify/save a custom deck, play normal matches in both starting positions, and inspect evolution and placement development. Assess the alternative decks and the reported Constructs weakness with human playtesting.
5. For an existing account, refresh and preview again after activation. Confirm only its original Kindred's additional ten bound copies, including purchased/earned quantities in the before/after totals. Enter an explicit upgrade review reason and apply once.
6. Repeat the preview/application. It must report already granted without another acquisition. Publishing another recipe version must not create another forty-copy entitlement. Verify custom decks, existing matches, statistics and previous purchase/reward history remain intact.
7. Confirm these extra starter lots cannot be traded, and that owning more copies does not raise standard battle-deck copy limits. Check first-copy shop protection, logout/login and application restart persistence.
8. Review immutable grant history, configuration version, acquisition receipt and administrative audit history. Retain the backup and record human findings before selecting any hosted configuration.

Backfill never replaces a saved deck. Existing players may explicitly edit a deck or create a new one using the published recommended list.

## Hosted TEST review and activation

Routine application updates remain:

```sh
sudo kindred-update
```

No agent deployment or homeserver modification is part of this milestone. The updater's exact-commit CI policy, verified backups, isolated restoration/migration rehearsal and health/recovery safeguards remain required. Production starter activation remains disabled.

After the owner approves the exact definitions and decks, an authorized administrator can record the current recipe digest and an approval reference under **Record the owner's hosted review**, then publish the desired activation flags in hosted TEST. The backend checks that approval digest against the recipe. This is an administrator-recorded approval checkpoint, not an independent cryptographic owner signature. Do not enter an approval reference merely because automated tests passed.

Inspect an exact account preview before each hosted backfill. There is no automatic mass backfill. Changed ownership, content or configuration invalidates a stale preview. Accounts requiring original-Kindred review remain blocked.

## Pause and recovery

Publish a reviewed draft with both activation flags false to pause future grants. Previously issued lots and receipts remain; configuration rollback cannot erase ownership or reissue an entitlement. Historical starter configurations are revalidated before rollback.

If a grant response is interrupted, inspect grant history or repeat the same account operation; the transaction and fixed entitlement prevent partial or duplicate grants. If a wrong but valid selection was approved, pause grants and investigate the exact acquisition/audit receipts. Do not delete ledger rows or reset collections. Any correction requires an explicit audited administrative decision.

Use the existing [backup/recovery checklist](V1.5-OWNER-ACCEPTANCE.md#backup-and-recovery) and [operator instructions](V1.5-OPERATIONS.md). Restore rehearsals use a separate database. Never overwrite hosted data or start old images against a newer schema as an improvised rollback.
