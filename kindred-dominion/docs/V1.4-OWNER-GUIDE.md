# V1.4 owner launch and testing guide

This guide supersedes the historical development-dashboard launch flow. Node.js 24+, npm and PostgreSQL 15+ are required. This Windows machine uses PostgreSQL 18. Source, original artwork and runtime assets come from Git; browser-local Studio data is not required to play published cards.

## Open the configured game

The current local DEV target is `127.0.0.1:5432 / kindred_dominion_dev / kindred_dev`, a nonsuperuser account. The private configuration is `server/.env.local`; six additive migrations are applied and the illustrated founding catalog is already seeded. Credentials remain private. Do not reset or reseed an established database just to start the game.

```powershell
cd D:\kindereddominion\kindred-dominion
npm ci
npm run db:status
npm run dev:all
```

Open **http://127.0.0.1:5173/**. The API is loopback **3001**, proxied through the frontend; its readiness check is `http://127.0.0.1:3001/readyz`. If both services are already running, use the URL directly. To restart a launcher, use Ctrl+C in its terminal, then start it again. Do not launch a second frontend over an existing server.

For separate terminals, use `npm run backend:dev` and `npm run dev`. For compiled full-app testing:

```powershell
npm run build
npm run backend:build
npm run backend:start
# In a second terminal, from the same application directory:
npm run preview
```

The compiled and development alternatives use the same ports; stop your previous launcher first. PostgreSQL remains running across application restarts.

## Register and play

1. Choose **Begin your collection** or **Log in -> Create an account**. Supply a unique 3-32 character username, valid email, display name and matching 15-128 character passwords. Maximum encoded password size is 256 UTF-8 bytes. Ordinary registration always creates a player, including the first account.
2. Choose one of the five Kindreds and inspect its starter choice. Confirm once to receive its existing 30-card starting collection and exact 15-card recommended deck. The backend records a single atomic grant; refresh/login cannot repeat it. You do not receive all 150 cards.
3. **Card Catalog** shows all 150 published creatures; **My Collection** shows actual ownership and quantities. Search `A001`, filter Kindred/placement/rank/classification/mechanics/power/set, sort and inspect full-size cards. Ownership can include multiple copies without changing deck limits.
4. **Deck Builder -> Create deck**: name the deck, choose scoring/format/Kindred restriction, then add/remove owned cards and adjust quantities. You may start from **Use my recommended starter** or manually choose all 15. **Save draft** preserves incomplete work; fix the legality messages and **Save deck** to make it ready. Edit/rename, duplicate, delete and **Select for battle** are functional and persistent.
5. Log out, log in, and confirm the collection and deck remain. **Play** lets you select the saved deck, Classic or Domination, and a compatible published computer formation. Review the settings and choose **Begin match**.
6. Keep the five-card opening hand or select cards to exchange once. Select a hand card, choose a legal highlighted tile, review the action preview and confirm. Inspect printed and current power separately; tile ownership/tokens/fortifications and scores remain outside the face. The computer acts on the server. Complete the game normally, then review the result and **Match history -> Watch replay -> Final position**. Leaving the match saves it for **Play -> Resume**.
7. With the explicit DEV testing sampler enabled, **Card Packs -> Claim one testing sampler -> Open sampler** becomes available after a verified normal match. Default contents are A001, M001, C001. Review received cards and quantities. Repeat review does not grant again. Sandbox/practice does not qualify. This is a bounded testing policy, not the production economy.
8. Restart the frontend and API, retaining PostgreSQL and the same private configuration. Log in again if necessary; ownership, quantities, preferred deck, match history and verified statistics remain. Settings also supports current-password-protected email/password changes and a device-local reduced-motion preference.

This machine explicitly enables local registration and the testing sampler for owner playtesting. The example configuration defaults to invitation registration and disabled testing acquisition. Local registration and testing acquisition are forbidden in hosted TEST/PROD. The sampler's policy is one entitlement per account; changing its configured contents does not create a second entitlement.

## Authorize your registered account

Register your account first. In a private terminal on this trusted development computer, replace all occurrences of `YOUR_USERNAME` below with the exact registered username (no angle brackets):

```powershell
cd D:\kindereddominion\kindred-dominion
node --import tsx server/cli.ts role --username=YOUR_USERNAME --role=administrator --confirm-user=YOUR_USERNAME
```

Use `--role=developer` instead for development-only privileges, or `--role=player` to revoke development access. The exact repeated username is required and the change is audited. No privileged password or automatic first-account promotion exists. Reload the full application (or log out/in); **Developer Studio** appears. This guide intentionally does not guess which of your accounts should be promoted.

In **Developer Studio**, initialize an empty private workspace, then open it. New workspaces start with the current published founding content and retain historical versions/recovery snapshots. Existing drafts remain intact. Edit a card from **Card Library**, or **Create card**, upload an illustration, configure its definition/influence/abilities and save. The shared renderer produces the live preview. Private changes stay in this account's server workspace.

Use **Battlefield Sandbox** to construct/save/execute a scenario and record a sandbox replay. It cannot affect ordinary inventory, match statistics or progression. **Content Versions and Backups** retains existing validation, checkpoints, approval/export and explicit backup/import tools. Repository publication remains the reviewed importer/commit workflow in [the artwork guide](V1.2-ARTWORK.md), not an automatic publish-to-live button. Unapproved draft artwork is never silently published. Return through **Return to game -> Main menu** to play with the same account.

The player-only build deliberately has no Studio, even for privileged users. Use the full authenticated application for development; server authorization is always required for private operations.

## First setup on another development computer

```powershell
cd D:\kindereddominion
git pull --ff-only origin main
cd kindred-dominion
npm ci
npm run backend:configure
```

The configure command accepts a hidden database password and creates/preserves a private `server/.env.local`. Configure the actual local database/role first. Review only the non-secret target through `npm run db:status`. Generate/preserve the session secret, choose local or invitation registration, and keep the loopback origin consistent with the frontend. For a new empty authorized DEV database, run `npm run db:migrate`, then `npm run db:seed`. For an existing database, take/restore-verify a backup before additive migration; never reset it. Start with `npm run dev:all`.

Invitation mode requires an operator-issued invitation: `node --import tsx server/cli.ts invite` prints a private filename containing the invitation code. Do not publish that file. Email address verification and email delivery are not configured. DEV recovery uses `node --import tsx server/cli.ts recovery-code --username=YOUR_USERNAME --confirm-user=YOUR_USERNAME`; enter the privately stored, expiring single-use code under **Log in -> Recover an account**. See [account security](V1.4-ACCOUNTS.md).

## Database backup and restoration

```powershell
node --import tsx server/cli.ts backup --with-source --directory=.local/v1.4/backups
```

Run from a clean committed source tree. This produces a private custom-format PostgreSQL dump, SHA-256/count/content/migration receipt and verified Git source bundle. Keep the receipt, dump and source bundle together on an independent backup device; GitHub contains the committed artwork/content, not your accounts or private drafts. Preserve backend/session configuration separately in private storage.

Restore verification uses the existing separately owned disposable PostgreSQL instance:

```powershell
node scripts/pg-isolate.mjs resume
node --import tsx server/cli.ts restore-test --file=D:/path/to/private-backup.dump
```

The command creates a new `kd_restore_*` database, verifies counts, published checksums, replay records, workspaces and the inventory ledger, and writes private `.local/v1.3d/restore.env`. It never replaces DEV. To inspect/migrate only that restored copy in PowerShell, set `$env:KINDRED_ENV_FILE='.local/v1.3d/restore.env'`, then use `node --import tsx server/cli.ts status` / `migrate`. Remove that override afterward with `Remove-Item Env:KINDRED_ENV_FILE`. Do not point the normal owner launcher at the disposable database accidentally.

The read-only `scripts/verify-migration-preservation.mts capture|verify .local/<receipt>.json` records counts/hashes of every pre-existing data column; migration ledgers are excluded because migrations intentionally append to them. V1.4 rehearsed restoration and both migrations on a new copy, then repeated the preservation check on DEV. A rollback/restoration into an established owner database remains a deliberate operator recovery action; do not run destructive restore/reset commands as startup steps.

## Build and validation

```powershell
npm test
npm run build
npm run build:player
npm run backend:build
npm run validate:assets
npm run validate:backend-isolation
```

`dist` includes the full application; `dist-player` excludes Studio/laboratory/unapproved assets; `server-dist` contains the compiled backend/CLI. The player preview uses `node node_modules/vite/bin/vite.js preview --outDir dist-player --host 127.0.0.1 --port 5173 --strictPort` with the same backend running. The official package carries 150 runtime illustrations plus crest/fallback, with original masters kept separately in Git.

The acceptance report records the separate isolated-database browser/test commands and results. Synthetic integration tests refuse owner DEV. Physical Android/iOS acceptance, Docker execution, Ubuntu deployment, email delivery/verification and a production pack economy remain outside the completed local acceptance. A016/A018 artwork numeral exceptions remain recorded. No rules, balance, IDs, evolution links or image bytes changed.
