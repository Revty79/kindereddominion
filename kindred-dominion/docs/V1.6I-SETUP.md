## Administrator workflow

1. Sign in with the existing trusted administrator account, open **Administration → Setup and readiness**. The ordinary dashboard and all manual controls remain available. Developers and ordinary players cannot open setup APIs or private configuration history.
2. Check the environment banner and database/migration readiness. A blocked database check requires the trusted operator; the browser cannot migrate, reset, repair, promote an account or change server environment variables. Pending or mismatched migrations prevent dependent inspection. No database credentials, database target names, session secrets, payment keys or webhook secrets are returned by the dashboard.
3. Review each status. **Complete** means the local server check passed; **incomplete** means no reviewed publication exists; **disabled** means a configuration or server capability is paused; **blocked** identifies a missing/invalid dependency; **optional** identifies a nonessential feature such as an empty limited catalog or disabled sandbox commerce. Optional cosmetics and sandbox commerce do not block ordinary play. Local readiness does not certify public connectivity, TLS, genuine Stripe verification or hosted acceptance.
4. Follow the suggested publication order or choose a guided step. Existing valid active versions are recognized, with no requirement to republish them. Review links lead to the relevant guided configuration or existing manual area.
5. Select **Create draft from current settings**, **Create draft from latest DEV proposal**, or resume an existing saved draft. The proposal values are visible in the existing structured controls and configuration document. Creating a draft never changes an active version. Proposals are provisional, not owner-approved permanent policy.
6. Edit and **Validate and save draft**, then **Preview publication dependencies**. The preview names the active version and changed fields; proposed values remain visible in the editor and prior values are available through history inspection. It runs the same publication validators used by the existing service, including content identities, immutable recipes, reward entitlements, currencies, artwork and edition promises. Every preview rolls back, even when an existing validator temporarily creates an identity/recipe during checking. The guide additionally orders runtime prerequisites such as Trading's economy account service. It does not loosen independent manual publication rules.
7. Resolve any named blocker, follow its navigation button and preview again. A successful preview does not reserve stock, grant assets or guarantee a future publication: the service revalidates at actual publication, and stale draft revisions or changed active versions are rejected. Guided publication stays disabled until the saved revision has a successful preview and a publication reason.
8. For starter approval, expand **Record the owner's hosted review**. Obtain the owner's approval for the exact recipe digest and enter that digest and approval reference explicitly. The draft preview reports its own recipe digest, including when hosted approval is missing. The guide never fills approval fields. Draft audit receipts retain the supplied approval/reference; normal hosted starter and deluxe checks remain authoritative. Isolated testing is not hosted owner approval.
9. Choose **Publish reviewed draft** explicitly. There is no publish-all, enable-all or silent replacement operation. Each publication uses the existing domain lock, expected-active-version check, immutable version, publication ledger and audit event. After publication, readiness refreshes and the next dependency can be reviewed.
10. Expand **Immutable version history and rollback**, then **Inspect published values** to read a historical document without activating it. Existing rollback requires its own reason and server validation; historical inspection is read-only.

Saved drafts, active versions, approval fields and histories are existing PostgreSQL records. They survive browser/application restarts and are shared with authorized administrators. The guided step is restored from the protected page's `#setup/<domain>` URL. Save edits before leaving a step; unsaved text is not a server draft. After a lost response, refresh and inspect saved drafts/history before creating another draft or publishing again. A lost successful publication is visible in immutable history and its original draft receipt.

## Dependency map

These are conditional dependencies, not blanket requirements to activate every system. The map inspects actual current publications, proposal values and real validator results.

| Configuration | Prerequisite and reason |
| --- | --- |
| Founding content | Approved repository content must be seeded/published through the existing trusted process. The dashboard checks all 150 founding permanent identities and collectible numbers against selected executable content. |
| Shop | Published gameplay identities. The default active Gold/Aether definitions allow initial bootstrap without a published economy. Custom acquisition currencies require the published economy. Enabled deluxe products require the exact approved starter recipe. Enabled limited SKUs require their published edition. |
| Limited editions | Underlying published shop cards/cosmetics/formats before a non-draft edition; the linked sale is enabled afterward. An empty catalog is optional and issues nothing. |
| Economy / currencies / progression / challenges / achievements | Published content. Entitlement rewards require the published shop and exact active booster/cosmetic. Limited rewards also require their published enabled edition and reserved allocation. Currency and objective settings belong to this same version. |
| Starter collections | Published content, valid owned-copy/deck recipes and immutable recipe identity. Hosted activation requires separately recorded owner approval of the exact digest. Published optional shop eligibility definitions are also checked by the real validator. |
| Trading Hall | Authoritative economy accounts/progression for runtime participation, plus its own published eligibility restrictions. The guide orders economy first; existing independent manual configuration remains supported. |
| Cosmetic products | Approved artwork and implemented published cosmetic identities in the shop; optional standard starter appearances retain their separate exact approval checkpoint. |
| Sandbox commerce | Published active Aether; fixed-content asset products require exact active shop components. Private environment configuration controls disabled/simulation/Stripe sandbox modes. Configuration publication alone does not enable a provider. |

If proposed custom currencies depend on an economy whose rewards depend on that proposed shop, the map reports a cycle. An administrator can explicitly review a base default-currency catalog or currency-only economy before adding dependent products/rewards. The wizard never removes entitlements or changes values to resolve a cycle automatically.

The latest commerce **proposal** now disables legacy asset SKUs whose components the curated shop proposal archives. Previously published catalogs, permanent identities and the historical default fixture remain unchanged. The validator names the exact missing component when a reviewed custom proposal still references an unavailable SKU.

## Safety and architecture

- `server/setup.ts` provides authenticated readiness and rollback-only previews. `server/setup-rules.ts` provides conditional edges, ordering/cycle detection and blocker navigation. `configuration.ts` exposes the same validator used by real publication and authenticated immutable version inspection.
- The setup interface reuses `ConfigurationEditor` and the existing starter/shop/economy/trading/commerce/limited structured tools. The manual publication/rollback controls remain available.
- There are **no new database migrations or setup tables**. No historical ownership, rewards, approvals or payments are fabricated. The runtime schema-readiness marker now points to the latest existing V1.6H limited-projection migration; an older schema cannot claim backend readiness.
- Administrator identity remains operator-provisioned. For an existing account, use the existing trusted `account:role` CLI with its explicit username/role/confirmation arguments; there is no unauthenticated provisioning endpoint.
- `ECONOMY_ENABLED` and `COMMERCE_MODE` remain private server controls. A paused server explains the disabled operations; it cannot be enabled from the wizard. Production economy and payment activation remain prohibited. Live credentials remain rejected by existing configuration loading.
- Stripe readiness exposes only mode and whether required sandbox settings are present. It never returns values or makes provider network calls. Presence is not a connection/webhook/payment acceptance receipt. Use the existing secure [Stripe readiness guide](V1.5F-STRIPE-READINESS.md) for privately entering credentials and genuine sandbox verification.
- Existing updater trust workflows and operator implementation are unchanged. Routine eligible hosted TEST updates remain `sudo kindred-update`, including self-update, backup, isolated restoration/migration rehearsal, preservation and health checks. No SHA argument, routine operator reinstall or manual GitHub approval is added.
