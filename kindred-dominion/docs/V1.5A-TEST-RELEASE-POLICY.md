# V1.5A TEST updater release policy correction

The owner's existing homeserver is private **TEST**. Its normal update command is **`sudo kindred-update`**, with no manual GitHub release approval, browser login or API credential. This document supersedes the original owner-approval requirement for TEST; [one-time installation and full recovery](V1.5-OPERATIONS.md) are the operating instructions.

## Policy separation

| Policy | Eligibility | Deployment authority |
| --- | --- | --- |
| `test-exact-main-ci-v1` | Exact main/push SHA has successful latest source-CI attempt, pinned workflow, correct repository and every job/step successful; runtime supports the TEST policy | Fixed homeserver TEST target only |
| `owner-dispatch-and-source-ci-v1` | Exact successful source CI plus explicit owner workflow approval | **Disabled** until separately authorized |

TEST makes credential-free public GitHub API reads. Its verifier never requests the manual approval workflow; an absent/failed approval cannot block a TEST revision that otherwise qualifies. Failed, pending, cancelled, skipped, missing, forked, wrong-commit and wrong-workflow CI cannot qualify. Discovery selects the newest qualifying forward main commit, never an arbitrary unvalidated branch head or a downgrade. If the eligible installed revision is healthy, the command reports up to date without rebuilding or migrating. API/network/rate-limit failures stop safely and explain how to retry.

Production eligibility still requires explicit approval. Even a valid production eligibility receipt has `deploymentEnabled=false`; the deployment permission check rejects it. Production enable flags are rejected, and the current adapter exposes no production target/CLI switch. Removing approval for TEST does not authorize production operation.

## Target safeguards and self-update

The root policy and code bind TEST to **homeserver**, `/etc/kindred-dominion/test`, **kindred_dominion_test**, local PostgreSQL 18 on port 5432, dedicated **kindred_test_migrator** and **kindred_test_runtime**, both private `APP_ENV=test` files and the actual database's **test / disposable=false** guard. Existing host/network, role privilege/ownership, path, HTTPS, storage and private-file checks remain. The actual database identity and guard are rechecked before discovery/self-update and before migration/start; a production guard fails even if a file or database is named TEST. The candidate adapter independently verifies receipt scope against that target.

Runtime metadata explicitly advertises TEST-policy support. Green historical source CI alone cannot install the older owner-login runtime and silently revert TEST to manual approval. The verified immutable-bundle handoff still holds one exclusive lock, checks every retained file, runs its credential-free import probe, atomically activates the pointer and preserves previous tooling. Pinned workflow trust cannot be replaced by an ordinary main commit.

The one-time `install.py --reviewed` upgrade recognizes only the exact legacy format-1 root policy with unchanged repository, owner IDs and workflow hashes. It saves the original bytes in a root-only hash-named policy backup and records the authorized policy transition before replacing it with format 2. Unknown/custom trust is refused. Repeat installation is idempotent. Application credentials/configuration, databases, backups, journals and services are not modified by installation.

All existing candidate builds/tests, networkless read-only unit validation, checksum/source-bundle backups, isolated restoration/migration rehearsals, preservation checks, migration uncertainty, compatible-image rollback, separate-database recovery, exact image/HTTPS health checks and deployment receipts remain. TEST receipts include the exact CI run/attempt, policy, environment and target. `--rehearse-only`, an explicit eligible revision, `--resume`, and `--recover-operator` remain advanced options.
