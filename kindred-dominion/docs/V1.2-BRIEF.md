# KINDRED DOMINION
## Development Stage V1.2 — Developer Studio and Balancing Infrastructure

## 1. Project Objective

Continue development of Kindred Dominion by implementing V1.2: a comprehensive, locally accessible Developer Studio for creating, managing, testing, balancing and versioning game content.

Existing repository:

https://github.com/Revty79/kindereddominion

Initial V1.1 reference commit:

`f953daadb9e0373f153491048b1d3d35de1aba88`

The owner has begun playing V1.1 and is generally pleased with the initial implementation. Gameplay familiarization and owner testing remain ongoing.

The owner has reported some difficulty following battlefield interactions and locating information, but has not authorized a redesign of the existing gameplay interface.

Do not attempt to solve those usability concerns prematurely.

V1.2 must provide the tools necessary to investigate those concerns, experiment with mechanics and eventually create the complete 150-card commercial library.

## 2. Preservation of V1.1

Before implementing anything:

- Inspect the current repository and working tree.
- Review the existing V1.1 documentation.
- Confirm the current application builds and runs.
- Run the existing automated tests.
- Establish a recoverable baseline.
- Preserve any existing owner changes.
- Record the baseline commit and validation results.

Do not overwrite or discard uncommitted owner work.

The existing V1.1 gameplay experience must remain available and functional throughout this stage.

Do not modify unrelated projects, including Serrian Tide.

Do not redesign existing game rules, rebalance existing cards or alter the default player experience without authorization.

## 3. Architectural Requirements

Continue using the existing React, TypeScript and Vite architecture.

Maintain a clear separation between:

- Core game engine.
- Card definitions.
- Tactical rulesets.
- Player-facing application.
- Developer Studio.
- Simulation infrastructure.
- Content persistence.
- Replay and diagnostic infrastructure.

The Developer Studio must use the actual game engine.

Do not create a separate simplified implementation of gameplay mechanics for testing.

All authored cards and rulesets must ultimately be interpreted by the same engine used during normal matches.

Continue supporting local operation without paid services, accounts, external AI APIs or a database server.

## 17. Automated Match Simulator

Implement a headless simulator that runs computer-versus-computer matches using the actual game engine.

The simulator must support:

- Selecting two test decks.
- Selecting a tactical ruleset.
- Selecting a battlefield configuration.
- Selecting a card-library version.
- Configuring the number of matches.
- Configuring a reproducible random seed.
- Alternating starting players.
- Running mirrored deck comparisons.
- Running multiple deck pairings.
- Running a round-robin test across selected decks.

Provide reasonable simulation presets, such as:

- 10 matches.
- 100 matches.
- 1,000 matches.
- 10,000 matches.

Large simulations must not freeze the browser.

Use Web Workers, batching or another appropriate nonblocking approach.

Provide:

- Progress indicators.
- Completed match counts.
- Elapsed time.
- Cancellation.
- Partial-result preservation.
- Error reporting.

Run simulations locally without external AI APIs.

Avoid unnecessary memory consumption, particularly when thousands of matches are executed.

Do not retain complete histories for every simulated match unless explicitly requested.

Retain representative results, reproducible seeds and diagnostic records for failed matches.

## 18. Simulation Safety

Establish a configurable maximum number of turns or actions for simulation purposes.

This simulation-specific limit must not silently change the normal game's completion rules.

A match exceeding the simulation limit must be reported separately from a legitimate win, loss or draw.

Track:

- Completed matches.
- Legitimate draws.
- Surrenders, if applicable.
- Simulation timeouts.
- Engine faults.
- Invariant failures.
- Infinite-loop safeguard events.

Never classify a faulted or interrupted match as an ordinary completed competitive result.

Every reported failure should include sufficient information to reproduce the scenario.

## 25. Actual Browser Acceptance Testing

Perform actual browser testing using Playwright or the existing browser-testing infrastructure.

### Workflow A — Create a card

1. Open Developer Studio.
2. Create a new draft card.
3. Assign its Kindred and basic statistics.
4. Configure territorial influence visually.
5. Assign a supported triggered ability.
6. Configure activation restrictions.
7. Save the card.
8. Reload the application.
9. Verify the card remains available.

### Workflow B — Test the card

1. Open the Battlefield Sandbox.
2. Create a relevant battlefield scenario.
3. Add the newly created card to a player's hand.
4. Execute a legal placement.
5. Inspect territorial and ability effects.
6. Reset the scenario.
7. Repeat the test.
8. Verify reproducible behavior.

### Workflow C — Test evolution and replacement

Create or edit test cards demonstrating:

- A specific-predecessor evolution.
- A classification-based evolution.
- A replacement with a sacrifice-triggered interaction.

### Workflow D — Run a simulation

1. Select two valid decks.
2. Choose a tactical ruleset.
3. Run at least 100 headless matches.
4. Inspect the results.
5. Reproduce the run with the same seed.
6. Verify deterministic results.
7. Test cancellation of a larger simulation.
8. Export the report.

Also demonstrate a larger simulation workload sufficient to verify responsive browser behavior.

### Workflow E — Replay a match

1. Complete a normal match.
2. Open its replay.
3. Navigate backward and forward.
4. Inspect a relevant ability-resolution sequence.
5. Verify the reconstructed final result.
6. Modify a draft card.
7. Verify the historical replay remains unchanged.

### Workflow F — Backup and restore

1. Create owner-authored content.
2. Create a named checkpoint.
3. Export a complete backup.
4. Restore or import the backup into an isolated test environment.
5. Verify definitions, relationships and supported artwork are preserved.
6. Confirm invalid imports do not damage existing content.

### Workflow G — Regression testing

Open the original game interface using the original V1.1 card library.

Play a complete match through ordinary gameplay.

Verify that the Developer Studio has not introduced changes to the approved gameplay rules, card definitions or normal match flow.
