## Implementation corrections

**Immediate placement:** `src/account/PersistentGame.tsx` now calls its existing authoritative action path directly when `useCardPlacement` chooses a legal destination. It removes the review/direct setting, staged confirmation state, placement confirmation buttons and preview-request gate. Hover, focus and held-drag previews remain separate and available before commitment. A rejected/illegal action cannot advance the turn. The synchronous busy lock, request identity, server revision validation, pointer/click suppression and uncertain-response reconciliation remain in place. Cancellation changes an uncommitted selection; it never undoes a committed move. Placement/ability presentation still begins from the accepted result.

**Readability:** historical battlefield power and its legend now say recorded rather than current. Existing card inspection retains explicit historical/arrival labels. The deck builder explains published templates in player language without milestone names or internal recipe identifiers.

**Floating artwork:** when a tactical preview changes the affected positions, the floating portrait is repositioned before paint. Its refresh cancels a pending frame callback before the immediate bounded paint; ordinary pointer movement still uses one scheduled animation frame. The existing overlap avoidance/hiding remains, preserving readable target/effect markers.

**Printed-card rendering:** unchanged printed faces and influence diagrams use React memoization during gameplay updates. Card, artwork, facing, scale and appearance-context changes still refresh the face; effective power, selection and other temporary overlays remain independent. This changes rendering work without changing card markup or rules.

**Validation correctness:** the inherited history test now captures the normal-match count at creation; a short valid match can finish before its final shared-state test case. The assertion still requires exactly one total ordinary result and no change from replay. Browser match helpers explicitly wait for an accepted presentation to finish before asserting the latest authoritative turn, retaining existing assertion timeouts and full animations. Legacy Studio cases run against the full compiled bundle; the ordinary player package continues excluding that tooling. Guest Settings acceptance now checks the V1.6F account-settings explanation, while authenticated persistence is tested against the actual backend.

The final repeat also exposed two timing-dependent fixture assumptions: viewport mechanic coverage may need another synthetic account after its first match, and legacy artwork activation must finish before leaving Studio. The former now waits for session loading and explicitly logs out through the UI before registering; the latter asserts the selected version is active before returning to play. Required mechanic coverage, publication/gameplay assertions and original timeouts remain intact.

## Complete player and ownership journeys

Each founding Kindred has an isolated real UI journey: register, select the explicitly enabled DEV proposal, verify 30 unique identities/40 copies and the recommended 15, create a custom deck from scratch, remove/re-add a duplicate, save/reload an incomplete draft, finish/save/select it, enter and complete an ordinary match, inspect/replay without mutation, restart/login and return to the same selected custom deck. These browser matches wait the real default 30-second reward minimum and require at least three human placements, eligible settlement, XP and participating-Kindred mastery.

Separate PostgreSQL journeys exercise the same combined pipeline, repeated previews/history reads, duplicate accepted-action requests and exactly-once settlement. Their elapsed-time fixture is explicitly aged on disposable matches; it is not presented as a wall-clock browser match. Declared common-snapshot development matches produce identical final engine states, action records, scores and results in all four explicit presentation modes.

A combined legacy-account case starts a match, edits its saved deck, purchases copies, applies four concurrent attempts at the fixed starter upgrade, settles an actual card trade, receives an achievement, equips an appearance and changes preferences. Match state, record, decks, configuration and revision remain identical. The trade makes a saved duplicate deck ineligible without changing its list, and a new match is rejected until explicit repair. Wallet/inventory ledgers reconcile. Temporary configurations and an existing approved illustration reused as a cosmetic are confined to disposable data; no founding content is published or changed.

The transfer fixture preserves provenance safeguards: administrator-funded acquisitions remain bound, and existing purchase holds are not undone by later trading-policy edits. Legitimate transfer coverage uses explicit promotional funding and a disclosed isolated zero-hold configuration before purchase. Ordinary security/economy policy is not relaxed.
