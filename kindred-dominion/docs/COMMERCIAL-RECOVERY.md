# Sandbox commercial investigation and recovery

All commerce remains sandbox-only. Simulations are not revenue, and sandbox accounts cannot enter ordinary player trading. These procedures do not authorize production activation, hosted database modification or an automatic homeserver deployment.

A Checkout return never grants assets. Signed events are durably retained, then current provider evidence verifies the exact saved order. Verified payments and delivery commit separately. If delivery fails, the payment remains recoverable and the goods transaction rolls back completely. The background worker retries retained events with expiring leases. Inspect the original order, provider identity, event history and pinned product before an administrative reconciliation. Never create a replacement payment to repair missing goods.

Refund requests persist their exact amount, reason, actor and idempotency key before contacting the provider. The external call holds no database transaction. Concurrent requests reserve the remaining refundable amount. If its response is lost, retain the request and source holds: the worker first searches the provider's refund metadata for the same saved request, then safely retries within its bounded idempotency window. Unknown outcomes beyond that window require investigation; they do not create a fresh refund automatically. Do not issue a second request merely because the first response was interrupted.

Refund/dispute observations retain every independently verified status, including later current-state observations of an older event. Successful refunded amounts are cumulative; paid history never regresses. Provider arrival order is not a financial ordering guarantee. Financial events with an unresolved order association remain retained and can produce a clearly identified resolved child event after trusted provider lookup. Raw customer, billing and card payloads are not retained.

Default disposition is review with source holds. Holds cover original currency, its explicit compensation returns, original collectible/cosmetic grants and acquisitions funded from that currency. Central wallet availability and acquisition-lot rules enforce the hold. Root holds also propagate through E's ancestry checks; transferred history remains intact. This is a movement restriction for investigation, not confiscation or a finding against a recipient. Existing administrative restrictions remain independent and cannot be cleared by commercial review. Active match snapshots and card mechanics remain unchanged.

Authorized administrators can record an investigation note, continue a hold, explicitly retain assets, or explicitly reverse safe original assets. Review confirmation pins both the current refunded amount and dispute state. A stale confirmation must be reviewed again. Every disposition is reasoned, retained and replay-safe. Retaining assets is an explicit sandbox case decision, not an automatic refund policy or an approved permanent commercial policy.

Safe original reversal supports cumulative proportional Aether: `floor(original Aether * confirmed refunded cents / original paid cents)`, less amounts already reversed. It consumes only the original currency source and explicit returned descendants. If those funds were spent or held elsewhere, the entire reversal rolls back; unrelated credits are protected. Inspect the derived shop purchases and mixed funding before a separate explicit decision. Full fixed-product reversal requires all original copies to remain available, unreserved and unrestricted, and each cosmetic to be the same current grant. Partial fixed-product refunds require review; the system does not choose arbitrary cards to remove. Equipped original cosmetics are unequipped only on successful explicit revocation. Pack results, reveals, lifetime first-copy acquisition and old match artwork remain historical records.

Pending or failed refunds do not become successful refunds through a browser message. Failed provider refunds preserve observations and can release only the associated commercial holds when no other risk or explicit investigation hold remains. Dispute wins remain held until an explicit review. Open/lost disputes cannot silently trigger a refund-based asset reversal. Live-mode keys, events and production mutations are rejected.

For database recovery, use the existing operator's verified backup, isolated restore and migration rehearsal. Private local paired receipts contain database hashes, replay checks, Studio checks, ledger reconciliation and the matching committed source bundle. Restore to a separate database and verify before any authorized switch; never overwrite a live target to test recovery. Credential files are excluded from source bundles and must be backed up/restored separately in secure owner-controlled storage. The owner's routine TEST update remains `sudo kindred-update`; no routine reinstall, manual Git fetch, SHA argument or GitHub approval is introduced.

Genuine Stripe testing follows [STRIPE-SANDBOX-SETUP.md](STRIPE-SANDBOX-SETUP.md). Independent automated provider simulations are separate evidence. Stripe references: [refund creation](https://docs.stripe.com/api/refunds/create), [dispute retrieval](https://docs.stripe.com/api/disputes/retrieve), [event delivery and signatures](https://docs.stripe.com/webhooks). Permanent refund policy, live provider/business acceptance, tax/accounting/legal review and mobile purchasing rules remain owner-dependent future release decisions.
