# V1.6F — Last Move and player presentation preferences

Date: 2026-11-27. Implements [the owner assignment](V1.6F-ASSIGNMENT.md) upon V1.6E commit `f01795532f10055b4f1b214cd617c1ae2695883d`.

## Implementation

The player battlefield has **Last Move** and **Display** controls. Last Move opens a nonmodal inspection panel beside the historical battlefield; the established board, hand and essential-control viewport allocation is preserved. It selects the latest accepted action and allows switching between the latest player and opponent actions. Recorded actor, card artwork/number/rules, placement location, ability activation, affected tiles, lifecycle effects, numerical changes and previous/resulting scores remain readable.

The battlefield and scores explicitly say **HISTORY — NOT LIVE**, with a dashed border and a separate historical heading. The final move view highlights its recorded affected positions; individual steps show the selected effect, actual source/direction and numerical badges. Before/after tables compare public values. Played cards and creatures at a recorded step can use the existing enlarged-card inspection renderer. Arrival power is labeled separately from power at a selected historical step; neither is called current live power.

Replay uses V1.6E's presentation primitives: beginning, stop/pause, previous/next step, final recorded result and immediate **Current game** return. Returning restores focus to Last Move. Opening inspection cancels an uncommitted gesture and skips any old automatic presentation. Historical tile interaction is read-only card inspection; it cannot submit placement. Keyboard, native buttons and touch controls remain available. The panel scrolls internally when needed; the battlefield and outer gameplay page do not acquire scrolling.

## Recorded public history

Additive migration **23**, `1797500000000_presentation_history.cjs`, creates:

- `kd.match_recent_presentation`: one bounded row per match, retaining the latest move for each actor.
- `kd.player_presentation`: per-player preferences with an optimistic revision.

No existing account, match, deck, inventory, artwork or economy row is backfilled or rewritten. Readiness now requires migration 23 so the new backend cannot appear ready with its required tables missing. Previous migration sources/checksums and updater trust workflows are unchanged. Destructive down migration is disabled.

Accepted actions update the public sidecar in the **same existing transaction** as the match/action record and ordinary settlement. A browser animation, inspection or replay does not determine whether that transaction commits. Each public move retains its stable action identity, actor, action type and match revision. It stores one initial **public battlefield** and cell/score/turn deltas for subsequent presentation events, avoiding repeated complete match states or full-board snapshots for every event. There are no hidden hands, draws, seeds/RNG, activation histories, diagnostic contexts, private decisions or full engine records in this sidecar.

History uses the actual V1.6E accepted observations. Reading or replaying history does not call `act`, `replayAt`, the AI or another gameplay endpoint. The client expands stored public deltas only; it does not infer or simulate missing effects. Repeated inspection/replay reuses the current match/revision cache. A restored match reads `GET /api/matches/:id/recent-presentation` once when needed. Ownership, current revision and its corresponding history are selected in one PostgreSQL MVCC snapshot, so an action committing concurrently cannot pair an old revision with newer/missing sidecar data. Revision-qualified stale requests return 409.

Retention is limited to two moves, 96 events per supported move, 160,000 encoded UTF-8 bytes per move and 300,000 bytes for the complete compact payload. The database additionally enforces a 512 KiB JSON text limit. If necessary, older detail is replaced by an explicit unavailable marker, prioritizing newer information. A truncated/over-budget resolver stream is also marked unavailable rather than reconstructed from private or incomplete state. The match and ordinary log remain available. Older matches without a sidecar are playable and honestly report that details were never recorded. The migration does not fabricate historical presentations.

## Authority and recovery

The latest persistent match prop, automatic live presentation queue, historical selection/replay and input availability remain separate. Entering historical mode does not overwrite the live match or its scores/turn. Every return to gameplay uses the latest received authority; ordinary submissions retain server revision checks and request deduplication.

Incoming newer authority closes inspection/replay, notifies the player and preserves its newer durable recent history. The ordinary background match read continues independently. Abandoned history reads are aborted and guarded by generation/match/revision checks. Browser focus loss, hidden documents, resize, cancellation and unmount release timers/animations and return safely to the current position. Preferences changing during playback stop the presentation safely. Automatic replay has the existing 6.5-second budget; manual stepping can remain open without changing any server deadline. No multiplayer transport or turn timer was introduced.

Snapshot gesture cleanup now runs before paint, preventing a changed authoritative snapshot from inheriting an uncommitted selection during rapid/Instant interaction. V1.6C review/direct, drag, keyboard, touch, duplicate-submission and lost-response protections remain in place.

## Account preferences

`GET`/`PUT /api/preferences/presentation` require an authenticated account; writes use the existing origin/CSRF controls, strict field validation and a 30-save/minute account limit. Concurrent device saves serialize through the existing player identity lock and require the expected preference revision. A stale editor must explicitly reload; it cannot silently overwrite another device's settings. The Settings view is keyed by account identity. Defaults require no account write, and unknown/missing preference data safely normalizes to supported values.

Settings are available from the main Settings screen and the battle's Display panel:

| Mode | Behavior |
| --- | --- |
| Follow device setting | Default: reduced presentation when requested by the operating system, otherwise Normal |
| Normal | Standard ordered presentation; an explicit choice can override the system motion default |
| Fast | Same event order with half-length timing, including card movement |
| Reduced motion | Immediate accepted result with a readable static summary; manual replay uses readable steps without spatial flight or pulsing |
| Instant | Immediate accepted result; Last Move can start at the first recorded step for manual inspection, with no forced animation |

Implemented independent switches control card movement, ability effect animation, score animation, resolved-effect highlighting and live effect descriptions. Historical text stays readable even when live descriptions are disabled. No future audio or other nonfunctional controls are exposed. Card dragging remains an intentional input gesture; these settings control presentation animations. Loading/unavailable preferences do not block gameplay; known preferences or device-safe defaults remain usable. Settings refresh on focus/online and through a bounded interval for other-device compatibility.

The former unscoped device-local checkbox is replaced in the player Settings screen. Its local value is not silently copied into another account. Players can explicitly save Reduced motion or another mode to their account. Legacy offline practice retains its existing device-local presentation controls; this milestone applies to persistent player battles.

## Known limits

1. Physical phone/tablet behavior, motion comfort and preferred pacing still require owner acceptance; emulated browser coverage is technical evidence.
2. Old, unsupported or oversized historical detail is explicitly unavailable. No private engine replay is used to fill gaps. The bounded latest-per-actor history is not an archive of every past action.
3. Automatic replay can reconcile at its time budget; retained supported steps remain manually inspectable. It never pauses a server deadline.
4. Legacy offline practice controls and multiplayer transport remain outside this persistent-battle implementation. No gameplay, balance, card identity, artwork or commercial policy change was introduced.

No homeserver deployment was performed. The owner's TEST update remains `sudo kindred-update` after exact-commit CI eligibility; no required SHA argument, manual release approval or operator reinstallation was added.
