# V1.6I.6–9 — Tactical rulesets and capacity

## Authoring and publication

The original Classic/Classic Duel configuration and permanent founding identities are unchanged. Editing a built-in rule saves a separate experiment. The existing editor retains dimensions, starting-owner/token/fortification painting, resource caps, deck/opening sizes, default duplicate limits, collection restriction, Standard/Free Play format, Classic/Domination scoring and engine safeguards.

Custom rules are not silently converted to a 3×5 board or 15-card deck. Deck testing now respects the selected rule's format unless Free Play is explicitly selected as an override. A twenty-card/seven-card-opening experiment is verified through the actual match constructor and gameplay, not only stored in a form.

Save a draft before **Publish private ruleset revision**. Publication creates a new immutable `Workspace.rulesetVersions` entry with ID, monotonic integer revision, name, full configuration, completion condition, content ID, timestamp and private-testing classification. The history supports inspection and **Restore revision … as draft**. Restoration changes an editable draft; publication requires another explicit action. It never rewrites an older revision.

The protected and local stores preserve this ledger during backup/draft recovery and reject conflicting edits to an existing ID/revision. Older workspaces need no republishing or invented backfill. **All preserved private ruleset revisions** also exposes history for rules absent from a restored draft. Existing full backups include the optional ledger; existing ruleset entity exports remain editable rule definitions. Scenario regression exports include their pinned revision and full snapshot.

Saved scenarios and laboratory match records pin their actual rule revision when published. Unpublished or historical constructions retain their captured configuration and clearly identify the absence of a publication number. Ordinary account matches continue to pin their immutable content version, complete match configuration and replay initial state; no Studio draft is selected for them automatically. Battle receipt details expose the configuration actually captured by that match. Revisions never update an already-started match in place.

## Supported versus inactive settings

| Setting | Current executable capability |
| --- | --- |
| Battlefield | Configurable rows/columns, explicit starts, per-cell owner/tokens/fortification |
| Decks | Configurable deck/opening sizes and Standard default copy cap, with existing per-card limits |
| Eligibility | Existing collection restriction, Standard/Free Play and per-card restrictions |
| Scoring | Registry-backed Classic and Domination; printed scoring effects remain active |
| Turns | Existing two-participant alternating action/draw sequence and one opening exchange |
| Completion | Two consecutive passes or active-participant surrender, with existing fault/safeguard handling |
| Custom turn/victory scripts | Inactive; requires new engine behavior and compatibility/versioning work |
| Arbitrary ruleset-specific card lists | Inactive; existing collection/copy rules must not be presented as a general eligibility language |
| Teams, registration-order starts and more participants | Inactive; V1.7 dependencies below |

The editor explains inactive settings rather than presenting controls that appear to work. Extra data in an imported configuration does not implement a new turn, team or victory rule; executable capabilities remain the ones listed above. This assignment does not change rules or introduce new victory/turn mechanics.

## V1.7 multiplayer dependency assessment

| Existing two-participant assumption | Required future work |
| --- | --- |
| `Player = 0 | 1`, two player-state/deck/score arrays | Versioned participant/team identities, variable roster and migration/compatibility design |
| `1 - player`, alternating turns, two-pass completion | Explicit turn order, elimination/pass policy and ruleset-defined termination |
| Jade/right and Amber/left, horizontal pattern reversal | Ruleset-defined seat/orientation policy and readable multi-team ownership |
| Friendly/enemy predicates and one opposing side | Team relation evaluation, individual/shared territory and multi-team targeting semantics |
| Starting groups currently accept players 0/1 | Registration-order assignment, configurable participant/team starts and validation |
| Computer opponent and single account owner of a saved match | Authenticated roster, authoritative multi-client commands, reconnection and hidden-information projections |
| Two-column row/column scores and result winner | Team/free-for-all scoring, ties, inspection and match result contracts |
| Single-player-versus-computer reward evidence | Tournament eligibility, result integrity and separately approved reward policy |
| Public bounded presentation and actor-specific records | Multi-viewer projections and consent-safe hidden information for every seat |

Reusable seams remain: data-defined card/Kindred identifiers, configurable battlefield/starts, registry-backed mechanics/scoring, exact content/config snapshots, immutable rule revisions, engine version compatibility, pure simulation/replay and the separate battle transport/presentation boundary. A future engine version can extend these without changing the permanent founding IDs. Existing matches must remain on their compatible engine and snapshots.

No team rules, generalized networking, free-for-all engine, new tournament rewards or V1.7 implementation began in this assignment.
