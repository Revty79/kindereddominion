# V1.7 multiplayer readiness — design handoff only

V1.6G review, 2026-11-27. No multiplayer, matchmaking, transport, tournament or turn-timer implementation is included. The owner must discuss and approve V1.7 requirements before that work begins.

## Existing authoritative contract

The player chooses a saved, owned and legal 15-card deck. `/api/match-options` supplies reviewable deck/configuration information; `POST /api/matches` validates it again and freezes executable content, configuration, deck instances, engine version and commercial/economy context. Later edits, ownership transfers, grants or cosmetics do not replace the engine snapshot.

`POST /api/matches/:id/actions` accepts `{revision, requestId, action}`. Supported current actions are mulligan, play, pass and surrender. The server authenticates ownership, locks the match, checks request deduplication and revision, injects the authorized actor, validates the action and runs the existing engine. A revision covers the complete accepted human action plus any immediate computer replies. Match state, replay/actions, request receipt, ordinary settlement and recent public history commit together. Duplicate requests and stale revisions return 409; a duplicate is not another accepted action.

The browser submits a legal click, tap or drop immediately. A synchronous busy lock covers overlapping pointer/click/drop events. It retains the original request identity after an uncertain failure and reads saved authority before allowing a retry. This behavior is not an undo contract. A committed move cannot be cancelled by stopping an animation or navigating away.

## Public projection and private boundaries

The ordinary match projection exposes the local player's hand, public battlefield, public discard information, counts, scores and current legal actions. It excludes the opponent's concealed hand/draw identities, private random seed/state, future random results and diagnostic internals. Tactical previews stop at private/random boundaries and label uncertainty; they do not consume randomness or mutate the match.

V1.6E `ResolutionBatch` schema 1 carries ordered public observations: actor, revealed card, representative hand origin, placement destination, influence, abilities, effects and scores. An opponent origin represents a concealed hand area, never a known hidden slot. The client renders accepted observations and cannot create an effect by animating it.

V1.6F stores a bounded schema-1 public sidecar in the same action transaction: latest move per actor, at most two moves; one initial public board plus deltas; 96 events per supported move; 160,000 bytes per move and 300,000 bytes overall. Unsupported detail is explicitly unavailable. History ownership/revision reads share one PostgreSQL snapshot. Manual replay expands public deltas without calling the engine or action API.

The ordinary saved replay endpoint validates the stored record server-side and returns public projected frames. Private developer diagnostics deliberately contain both hands and the seed, require privileged role plus current match ownership, and record an audit event. Future PvP authorization must explicitly review that privileged boundary; it must not be copied into participant or spectator access.

## Presentation, reconnection and timing

Live authority, automatic presentation and manual historical inspection are separate. Presentation never gates a transaction or ordinary reward. Normal/Fast/Reduced/Instant preferences are per account and change visual timing only. Live and manual queues have cancellation/cleanup and a 6.5-second automatic presentation budget. A newer authority revision closes stale historical inspection, preserves the new history and returns to current play. The player can inspect the final result afterward.

Current saved-match reconciliation reads on focus/online and at a bounded interval. This is recovery for the existing computer-match application, not real-time multiplayer transport. Turn deadlines are not implemented. Future deadlines must be server-owned timestamps independent of browser animation, visibility, reconnects or replay. A slow or disconnected client must not extend them.

For reconnects, V1.7 needs an authoritative snapshot plus a revision-qualified event continuation, explicit action acknowledgement and a full-refresh fallback when retention gaps occur. Do not infer that an uncertain local action committed merely because some other participant advanced the revision. Use accepted action/request identities to distinguish it from a remote action.

## Missing prerequisites requiring V1.7 design

| Area | Present limitation / required decision |
| --- | --- |
| Participants | Matches belong to one account and a computer. Add explicit participants and participant authorization; preserve old computer matches. |
| Viewer projection | Local player is currently actor 0/Jade, opponent actor 1/Amber. Generalize viewer-relative hand/legal-action projection and labels without swapping permanent card identities or engine ownership semantics. |
| Turn transactions | The current endpoint resolves the AI in its transaction. Define one authorized remote action per turn and remove only the computer-specific loop for PvP matches. |
| Transport | Choose authenticated polling/SSE/WebSocket behavior, ordering, retries, disconnect policy, rate limits and operational support. No transport is selected here. |
| Revision contract | Define snapshot/event cursors, action acknowledgements and resynchronization. Never apply stale or out-of-order commands. |
| Privacy | Specify participant, owner/operator, historical replay and spectator permissions. Never broadcast a shared private engine object. |
| Timers | Define server deadlines, clock synchronization, reconnect grace, timeout outcomes and recovery. Animation preferences cannot affect these rules. |
| Persistence | Preserve immutable decks/content/configuration and action history across server restarts. Define transaction ownership and notification-after-commit semantics. |
| Economy | Define legitimate PvP settlement, arranged-win/farming controls, eligibility and audit sources before enabling rewards. Current computer-match policy is not automatically PvP policy. |
| Spectators/archive | Latest-two public history is not a complete archive or spectator feed. Define delayed visibility, retention, consent and recovery independently. |
| Account safety | Review simultaneous sessions, participant restrictions, abandonment, private diagnostics and administrative investigation. |
| Operations | Load/concurrency tests, multi-instance notification durability, restart/reconnect rehearsals, monitoring and owner-hosted acceptance remain required. |

The current public event and presentation separation can be reused. The account/participant model, viewer authorization, remote action transport and server deadlines are substantive missing prerequisites. This document does not claim multiplayer is ready to activate.
