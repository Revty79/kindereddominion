# Permanent homeserver TEST operations

This is trusted, local Ubuntu 24.04 operator tooling for **homeserver / 10.0.0.242**, PostgreSQL 18, and **kindred_dominion_test**. It never SSHs to a server. This work did not connect to or modify the live host. Hosted acceptance belongs to the owner and Ember using the normal update command; its mandatory isolated rehearsal is automatic. A separate rehearsal-only command is optional.

## Install the automatic updater once

Routine operation is **`sudo kindred-update`**. Release publication is a separate maintainer action on GitHub; the server never treats every main push as approved.

Before this first installation, review the published correction commit and wait for **Validate Kindred source** to succeed on that exact revision. On GitHub, open **Actions ? Approve Kindred release ? Run workflow ? main** using the Revty79 owner account. Wait for its green completion. This records owner approval of the immutable dispatch SHA; the workflow verifies exact source CI. The updater independently checks both runs, their latest attempts, jobs, steps, repository/actor IDs, branch and pinned workflow bytes. It rejects arbitrary pushes, fork runs, other actors, skipped tests and changed approval workflows. No dashboard product, webhook, token or server credential is involved.

The commands below are the **one-time upgrade from the old pinned operator**. Replace `<REVIEWED_SHA>` with the full commit supplied in the handoff. This is the only installation step that selects source manually. Stop if tracked changes appear; preserve them and the ignored `.env` rather than resetting, stashing or cleaning.

```bash
cd /srv/kindred-dominion/source/repository
git fetch origin main
git status --short
git show --stat <REVIEWED_SHA>
git switch --detach <REVIEWED_SHA>
sudo python3 -E -s -B kindred-dominion/deployment/operator/install.py --reviewed
sudo kindred-status
sudo kindred-update
```

After this installation, the normal procedure from any directory is just:

```bash
sudo kindred-update
```

No routine fetch, checkout, SHA, review flag, rehearsal command or reinstallation is required. The command selects the newest approved forward main release (up to 200 first-parent commits); explicit approved revisions can be selected outside that discovery window. If only the running revision is eligible, it checks health and reports **Kindred Dominion is up to date** without rebuilding, backing up or migrating. If no release qualifies or GitHub verification is unavailable, it fails before application downtime. A failed or pending latest approval/CI attempt invalidates older green attempts for that SHA.

Prerequisites remain the existing Docker Engine/Compose with `up --wait`, PostgreSQL 18 client tools under `/usr/lib/postgresql/18/bin`, Python 3.12/stdlib, Git, `ip`, peer-authenticated local `postgres` DBA access and existing TEST runtime/migrator roles. No host Node/npm/pip or routine GitHub API token is needed. Public GitHub API availability/rate limits are checked fail closed.

## Verified operator self-update

The seven permanent wrappers call a stable root-owned launcher at `/usr/local/lib/kindred-dominion/launcher.py`. The launcher verifies the active runtime against root-only `/srv/kindred-dominion/state/operator-current.json` before importing it. Approved bundles live at `/usr/local/lib/kindred-dominion/releases/<SHA>/` and contain SHA-256-checked regular Git blobs, not executable files read from a mutable checkout. Root ownership, modes, canonical paths, file bounds, the protocol/file list, Python compilation and an isolated credential-free import check are required. Interrupted partial staging never becomes active. A durable atomic pointer switch retains `operator-previous.json`, the old bundle and `operator-upgrade.json`.

One exclusive lock spans preflight, approval, self-update, the new runtime handoff and the entire deployment. The new runtime uses its own deployment implementation while borrowing that still-open lock. Operator versions are retained after application failures so recovery uses the approved candidate's tooling. Neither self-update nor installation modifies private environment/network files, migrates data or deploys services on its own.

`/etc/kindred-dominion/test/release-trust.json` pins repository ID, owner approver ID and the two trusted workflow hashes. It is installed once as root-only and never silently replaced by an update or reinstall. Routine operator code changes within protocol 1 self-update automatically. Changing the stable launcher, approval policy/workflows or operator protocol is an explicit trust-root upgrade requiring owner review; it cannot silently broaden its own authority. Do not grant other GitHub users the owner's credentials or allow an approval workflow to run without reviewing its exact revision.

For each release, a maintainer pushes source, waits for exact successful CI, reviews it, and uses **Approve Kindred release** on main. The server operator then uses the same one command. Owner approval is never inferred from Git author names or the updater's legacy `--reviewed` flag. Release approval/run/attempt IDs are retained in selection and deployment receipts.

The [Vite temporary-file correction](V1.5A-VALIDATION-CORRECTION.md) is retained: the networkless read-only unit container has a bounded 64 MiB nonroot tmpfs at `/app/node_modules/.vite-temp`, separately from `.vite` and `.local`. Source and the rest of node_modules stay read-only. Do not modify the private Compose override for that separate validation command.

Preserve these existing files:

- `/etc/kindred-dominion/test/backend.env`: TEST runtime role and existing session secret.
- `/etc/kindred-dominion/test/migrations.env`: TEST migrator role and the same session settings.
- `/etc/kindred-dominion/test/compose.network.yaml`: external `kindred-dominion-net` default network and the existing maintenance `/app/.local` tmpfs.
- `/srv/kindred-dominion/source/repository/kindred-dominion/.env`: existing deployment revision/Compose variables.

The [override example](../deployment/operator/compose.network.example.yaml) documents the existing 128 MiB, UID/GID 1000, mode 0700 tmpfs. Do not replace the private override with this example or duplicate its mount in base Compose: Compose merges `tmpfs` sequences. Environment files accept literal single-line dotenv values, with no shell evaluation; unsupported quoting/duplicate keys fails before migration. Keep secrets out of command arguments and terminal transcripts.

`operator.json` selects the approved HTTPS origin and published content ID, never a password. Its defaults match the supplied host. If the temporary tunnel hostname changes, review/update this file and **both** existing private frontend origins together before operating. The tool does not restart the tunnel or alter origins automatically. Preflight requires dedicated nonsuperuser roles without role/database creation, migrator ownership of the TEST database/schema, runtime without schema CREATE/migrator membership, the existing TEST environment guard, network subnet `172.23.0.0/24` and bridge `br-kindred`.

## Routine commands

```bash
sudo kindred-update
sudo kindred-status
sudo kindred-backup
sudo kindred-stop
sudo kindred-start
sudo kindred-restart
```

Release selection pins an exact SHA internally; no deployment follows a moving branch. The selected commit must be reachable from fetched `origin/main` and descend from the running release. Tracked source must be clean. Release worktrees live under `/srv/kindred-dominion/releases/<SHA>/`; `.env` stays in its original private location. Actual running image IDs and OCI revisions are captured independently of the checkout's current HEAD. Existing images are preserved; mismatched existing SHA tags are refused, not overwritten. No image/network/volume pruning or Compose `down` is used.

Each mutating command acquires one nonblocking exclusive lock. Update verifies identity, canonical paths, private settings, target database and storage (at least 4 GiB plus four database sizes free on application/backup/Docker storage). It checks committed source/runtime artwork checksums, validates the Compose security/network/bind configuration, builds all three candidate images and runs source/unit validation with no database credentials or network **before stopping the game**. Candidate player/control source markers and protected file hashes identify the reviewed release.

Only Compose services `game` and `backend` in project `kindred-dominion` are stopped. Remaining TEST client connections cause a safe failure; the tool never terminates unrelated sessions. A private custom-format dump is checksum/archive-list verified beside a verified Git bundle, asset-manifest digest, original-column row hashes, migration/content state and immutable image receipt. A new random `kd_rehearsal_*` database is created using the local DBA, restored as the migrator, checked against every original row/column, migrated and seeded using existing shared validators, and checked again. Existing source data is never overwritten by rehearsal.

Only after that succeeds does the updater mark live database uncertainty durably, apply additive migrations to TEST, synchronize the reviewed repository publication, grant/verify runtime DML/sequence permissions, and compare existing player/deck/match/Studio/session/ledger data. It starts pinned candidate image IDs with `--no-build --wait`, checks both container health states, loopback readiness at `127.0.0.1:18083`, approved external HTTPS readiness and the exact public release marker. Completed deployment receipts live in `/srv/kindred-dominion/state/deployments/`; `current.json`, `latest.json`, private logs and backups are root-only. The database port and backend port remain private. DEV, the existing `kindred-dominion-tunnel` container and unrelated applications are never operated.

Advanced commands remain optional: `sudo kindred-update <APPROVED_40_CHARACTER_SHA>` selects an exact approved forward revision; `sudo kindred-update --rehearse-only` selects automatically and rehearses only. Explicit revisions still require the same approval, and `--reviewed` cannot bypass it.

`--rehearse-only` performs the real build, quiesced backup and isolated migration rehearsal, then resumes the previous application without migrating live TEST. It includes downtime for the consistent backup/rehearsal. Do not run concurrent external TEST maintenance. Restored databases, dumps, worktrees and images are retained; the operator must review storage/retention separately. There is no automatic deletion.

## Failure and recovery

**Before live migration:** a failed build never stops the working application. Failure after quiescing attempts to resume the previous pinned images only if private configuration and schema/content still match. Inspect `kindred-status` and the private log if readiness/resume failed. Dumps remain intact.

**Once live migration starts:** the journal records `databaseMayHaveChanged` before invoking SQL. A migration/publication/start/health failure stops candidate application writers and blocks normal start/restart/another release. No automatic older image or old dump is applied. Interruption, including an unfinished journal after a crash, remains uncertain until reviewed. A failed transaction can be inspected and resumed with the same candidate; do not assume every failed command rolled back everything.

After checking the log, migration ledger, private settings and any labelled one-off maintenance container left by interruption:

```bash
sudo kindred-status
sudo kindred-update --resume
```

Resume takes a **new** safety backup/rehearsal of the current state and never erases the earlier failure's uncertainty on a failed rebuild. It cannot combine with `--rehearse-only`. Do not manually start older images against a newer schema. One-off migration containers are labelled `kindred.operator.run=<journal ID>`; inspect only the exact recorded instance. Do not stop all Docker containers or all PostgreSQL clients.

If approval of that failed revision was invalidated, the owner must re-run its original **Approve Kindred release** run after exact source CI passes. Explicit/resume verification queries that exact SHA even outside the normal discovery window. Approving a newer main revision does not authorize resuming a different failed migration.

For a previous recorded deployment with exactly compatible schema/content, an explicit image rollback retains newer player data:

```bash
sudo kindred-rollback --to <RECORDED_DEPLOYMENT_ID> --reviewed
```

It creates and restores a safety backup, then starts the recorded old image IDs only after compatibility checks. It never restores a database over TEST. An incompatible rollback is refused.

For a schema-incompatible recovery, select a verified **pre-update compatible** backup:

```bash
sudo kindred-rollback --prepare-recovery /srv/kindred-dominion/backups/<BACKUP_ID> --reviewed
```

This stops application writers, preserves/restores-verifies **newer current data** separately, restores the selected older dump to a new random `kd_recovery_*` database, verifies every old row, applies runtime grants, and writes a private recovery plan. It does not rename, drop, replace or reconnect TEST. Writers remain stopped. A partially migrated backup that does not match its previous executable release is not a recovery target.

A trusted DBA must review reconciliation needs and approve the manual cutover. Retain the current database under the exact name `kindred_dominion_test_preserved_YYYYMMDDHHMMSS`; rename the plan's separately verified recovery database to `kindred_dominion_test`, using a local maintenance connection to **postgres**, with application writers stopped and no active clients. Preserve both databases and all private settings. Never use `DROP DATABASE`, an in-place `pg_restore --clean`, or discard newer transactions. Exact names must come from the plan and DBA review; the web application has no recovery/SQL control.

After that explicitly reviewed DBA operation:

```bash
sudo kindred-rollback --complete-recovery <PLAN_ID> --preserved-database kindred_dominion_test_preserved_YYYYMMDDHHMMSS --reviewed
sudo kindred-status
```

Completion verifies the preserved newer database against its safety snapshot, verifies restored TEST against the selected old snapshot/schema/content, applies grants and starts only the compatible recorded image IDs. It refuses mismatched data. Newer player data remains in the separately named database and safety backup for reconciliation. No database is automatically deleted.

## Operator-only recovery

If the launcher reports damaged active operator files, recover the retained **verified tooling only**:

```bash
sudo kindred-update --recover-operator
sudo kindred-status
```

This takes the same exclusive lock, verifies every previous runtime file against its retained root receipt, and atomically restores the operator pointer. It does not start/stop applications or touch database state. Existing migration uncertainty still blocks ordinary operation. After inspecting the failure, retry `sudo kindred-update` (or `--resume` for an uncertain migration). If both bundles are damaged, repeat the one-time installer from the exact reviewed clean Git revision; preserve all private files, backups and deployment journals. Never delete the migration journal to unblock startup.

## Validation and owner rehearsal boundary

Portable workflow tests: `python3 -B -m unittest discover -s kindred-dominion/deployment/operator -p 'test_*.py' -v`. These test fault ordering and safeguards through an adapter; they do not execute Docker. A separate Windows-native rehearsal used actual PostgreSQL 18 dump/restore and migration commands on the owned disposable cluster, including a deliberate transactional failure; see [validation](V1.5-VALIDATION.md).

For the filesystem-write regression, install the lockfile dependencies in a separate source checkout, then run `node scripts/verify-readonly-validation.mjs --root <SEPARATE_CHECKOUT_APPLICATION_DIRECTORY>` from the application directory containing the correction. It derives the allowlist and unchanged full-suite arguments from the operator itself, demonstrates the missing config-cache write failure, runs the full suite with the corrected paths, and verifies source writes remain denied. This native Node permission model needs Node 24 and Python, is for local regression only, and is not a replacement for the owner's Linux Docker rehearsal. No new host dependency is required for routine installed operator commands.

Owner/Ember must run the actual Ubuntu/Docker rehearsal, inspect private receipts, verify the restored sample records and failure behavior, and then accept the hosted installation. That environment-dependent acceptance remains explicitly pending. Neither portable tests nor native Windows PostgreSQL proof is reported as a successful container deployment.
