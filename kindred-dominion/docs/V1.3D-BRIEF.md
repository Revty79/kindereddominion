### 1. Objective

Implement the permanent storage architecture and backend infrastructure for Kindred Dominion.

Repository:

https://github.com/Revty79/kindereddominion

This assignment must follow successful implementation and validation of:

- V1.3A — Advanced Mechanics and Rules Engine Completion.
- V1.3B/C — Owner-Designed Founding Kindreds, Gameplay Readability and Server Preparation.

### 11. Starting Collections

Implement the permanent starting collection system.

When a new player begins:

1. Create their player account.
2. Allow them to select one of the five Founding Kindreds.
3. Grant exactly one copy of each of that Kindred's 30 unique cards.
4. Create the corresponding recommended 15-card playing deck.
5. Record completion of starting collection selection.

The five starting choices are:

- Nature.
- Mythical.
- Arcane.
- Undead.
- Constructs.

The starting collection grant must be atomic.

A failed request must not partially grant a collection.

Repeated requests, reloads or concurrent requests must not allow a player to receive multiple free starting collections.

The player may inspect the other collections before choosing.

Do not implement commercial purchasing or collection switching during this assignment.

### 25. Actual Browser Acceptance Testing

Demonstrate the following workflows through actual browser interaction.

#### Workflow A — New Player

1. Create a player account.
2. Log in.
3. Inspect the five starting Kindreds.
4. Select Nature.
5. Receive exactly 30 unique Nature cards.
6. Receive the recommended 15-card Nature deck.
7. Reload and confirm persistence.
8. Attempt to claim another free starting collection and verify rejection.

#### Workflow B — Persistent Decks

1. Create a legal deck using owned cards.
2. Save it.
3. Log out.
4. Log back in.
5. Verify the saved deck remains available.
6. Attempt to save a deck containing unowned cards and verify rejection.

#### Workflow C — Persistent Gameplay

1. Begin an authenticated computer-opponent match.
2. Play several turns.
3. Close or reload the browser.
4. Resume the same match.
5. Complete the match.
6. Verify match history and progression statistics.
7. Verify replay accuracy.

#### Workflow D — Cross-Device Persistence

Use a separate browser context with no existing local storage.

Log in to the same account and confirm that collections, saved decks and match history are retrieved from PostgreSQL.

#### Workflow E — Content Update

Publish a controlled test revision of a card.

Verify:

- Existing ownership remains unchanged.
- Existing saved decks remain valid.
- Existing matches retain their original definitions.
- New matches use the selected updated content version.

#### Workflow F — Developer Studio

Create and save a draft card or content revision.

Verify persistence across login sessions.

Confirm that an ordinary player cannot access or modify this content.

#### Workflow G — Backup and Restore

Back up the development database.

Restore into an isolated database.

Verify accounts, collections, decks, content versions, match histories and Developer Studio records.

#### Workflow H — Regression
