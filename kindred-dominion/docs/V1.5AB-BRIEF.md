### Existing server-specific Compose override

The existing override connects the Compose default network to the external kindred-dominion-net network.

It also provides the maintenance container with this temporary writable filesystem:

`/app/.local:rw,nosuid,nodev,size=128m,mode=0700,uid=1000,gid=1000`

This was necessary because the artwork validation and invitation-generation commands require temporary writable storage while the maintenance container's root filesystem remains read-only.

Incorporate or preserve this correction without weakening container security.

### Required update system

Create a documented installation procedure and permanent operator commands:

- kindred-update
- kindred-status
- kindred-backup
- kindred-rollback
- kindred-start
- kindred-stop
- kindred-restart

The updater must support an explicitly selected, reviewed Git revision and must not automatically deploy unvalidated work.

Required update behavior:

1. Acquire an exclusive update lock.
2. Verify server identity, deployment paths, environment, database target and available storage.
3. Verify clean tracked source.
4. Fetch and identify the requested release.
5. Record the existing application revision, image identifiers, database migration state and content version.
6. Validate and build the proposed replacement images before stopping the working application.
7. Preserve existing immutable images.
8. Stop only Kindred Dominion application writers.
9. Create a private, verified pre-migration database backup and corresponding source/content recovery receipt.
10. Rehearse database changes against an isolated restored database before live migration.
11. Apply necessary additive migrations to the verified TEST target.
12. Synchronize published content using the existing importer and validators.
13. Verify and apply required runtime grants.
14. Start the updated application.
15. Verify container health, local readiness and external HTTPS readiness.
16. Record the completed deployment.
17. Release the update lock.

The updater must stop safely on errors and distinguish failures before and after database migration.

Do not attempt automatic schema-incompatible rollback against the live database. Provide a controlled recovery process using a separately restored database where required.

Do not automatically delete newer player data.

Preserve:

- Player accounts.
- Password hashes.
- Permissions.
- Player collections.
- Decks.
- Match history.
- Private Studio workspaces.
- Acquisition records.
- Session configuration.
- Existing Cloudflare tunnel.
- All unrelated server applications.

Include backup integrity checks, isolated restore verification, private logs, disk-space safeguards, explicit rollback procedures and clear operator-facing error messages.

Never automatically prune unrelated Docker images, containers, networks or volumes.

Do not require the owner to manually repeat the previous lengthy deployment sequence for routine updates.

## Part B — Hosted Administration and Developer Studio

### Current problem

The owner has an administrator account but cannot access useful administration or development functionality from the hosted game.

The public player build intentionally excludes Developer Studio. Preserve that boundary.

Provide a practical, secure hosted administration and development surface using the existing PostgreSQL accounts and permissions.

The owner must not need to register a second account.

### Administrator interface

Provide a clearly identifiable administrator entry point for authorized users.

If the protected administration application requires a separate address, document and integrate that navigation appropriately.

Provide an administration dashboard with functional tools for:

- Player account search and inspection.
- Account status management.
- Player statistics.
- Invitation generation, listing and revocation.
- Authorized card grants.
- Authorized pack grants where supported.
- Grant history and reasons.
- Administrative audit history.
- Published content inspection.
- Developer Studio access.

Use existing server operations and audited database mechanisms wherever possible.

Do not expose nonfunctional controls as completed features.

### Permission boundaries

Maintain server-side authorization for every privileged action.

Ordinary players cannot:

- Access administration data.
- Access private Studio workspaces.
- Modify ownership records.
- Generate invitations.
- Grant themselves rewards.
- Change account permissions.
- Access unpublished content.

Developer privileges must not automatically provide administrator privileges.

Administrator promotion, deployment commands, database administration and equivalent sensitive operator functions must remain restricted to trusted server operators. Do not expose shell execution or arbitrary SQL through the web application.

Do not use hidden navigation as the sole security measure.

### Hosted Developer Studio

Make the existing Developer Studio actually usable by the owner's authorized hosted account.

Preserve its functionality:

- Browse published and private cards.
- Create new cards.
- Upload original artwork.
- Configure card definitions.
- Configure placement and power.
- Configure influence patterns.
- Configure supported abilities.
- Configure evolution and replacement relationships.
- Preview cards using the approved full-bleed renderer.
- Save private drafts.
- Validate content.
- Use Battlefield Sandbox.
- Manage content versions and backups.
- Prepare reviewed publication packages.

Keep unpublished assets and private workspace data separate from the public player release.

Retain the existing reviewed publication workflow and immutable published versions. Do not silently publish private drafts.

A new card using supported mechanics should require only artwork upload and gameplay configuration, not a new card layout or source-code modification.

### Deployment architecture

Prepare the necessary protected administration application build, container configuration, authentication routing and server integration.

Ensure ordinary player packages continue excluding development-only code and unpublished artwork.

Use the existing administrator account infrastructure.

Do not point a development server directly at the public internet.

Do not expose PostgreSQL or private API ports publicly.

Account cookies, CSRF protections, allowed origins and authorization must work correctly across the intended protected access method.

The owner's existing player account and collection must remain intact.

### Card acquisition preparation

The current local-testing sampler is deliberately unavailable in hosted TEST/PROD. Consequently, hosted players lack a complete ordinary card acquisition loop.

The owner and Ember are separately designing the permanent card economy, including currency, battle rewards, pack contents, pricing and shop rules.

Prepare compatible administration interfaces for existing authorized grants and acquisition history.

Do not independently finalize:

- Currency names or values.
- Match reward amounts.
- Pack prices.
- Pack sizes.
- Rarity distributions.
- Drop rates.
- Real-money purchases.
- Trading.
- Duplicate conversion.
- Production monetization.

V1.5C/D will supply the approved economy requirements.

## Acceptance requirements

Validate the following:

1. Existing V1.4 player data remains unchanged.
2. An ordinary player cannot access administration functionality.
3. The authorized administrator can enter the protected administration interface.
4. The same account retains its normal player collection and decks.
5. The administrator can generate and revoke tester invitations.
6. Authorized card grants are persistent, audited and duplicate-safe.
7. Developer Studio supports creating and configuring a private card.
8. Sandbox activity does not award normal player progression.
9. Unpublished content is not exposed to ordinary players.
10. The updater completes a reproducible isolated update rehearsal.
11. A failed build leaves the previous application working.
12. Database migration failures produce a safe, documented recovery state.
13. Backup restoration is demonstrated in isolation.
14. No unrelated server services are affected.

Provide screenshots from the actual administration and development application, test evidence, installation instructions and exact operator commands.

Commit and push validated work in separate logical milestones.

Do not connect to or modify the owner's live Ubuntu server without explicit authorization.

The owner will perform the actual server installation and acceptance with Ember.

The objective is to make Kindred Dominion independently manageable as an actual hosted game, not merely a local development application.
