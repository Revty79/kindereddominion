# V1.5A PostgreSQL rehearsal verification correction

The installed `c5946a6` operator reaches the post-publication privilege audit after isolated restore/migration. Its old query scans `pg_tables` and calls `has_table_privilege(..., 'kd.' || quote_ident(tablename), ...)` in the same WHERE clause as `schemaname='kd'`. PostgreSQL may push that function predicate down to the `pg_class` scan before the namespace join/filter. A real system-catalog name then becomes the nonexistent **kd.pg_statistic**. This is SQL generation/evaluation order, not a missing application table or a reason to grant access to system catalogs. [PostgreSQL expression evaluation rules](https://www.postgresql.org/docs/18/sql-expressions.html#SYNTAX-EXPRESS-EVAL).

The corrected audit materializes only **kd** ordinary/partitioned relations from explicitly qualified **pg_catalog.pg_class / pg_catalog.pg_namespace** and checks privileges against their actual **OID**. Sequence permissions use their own materialized sequence-only set; sequence privilege functions reject non-sequences, so a schema predicate alone is insufficient there too. Application snapshots use the same catalog scope and `pg_catalog.pg_attribute` with actual relation OIDs, require every original table/column to remain present, and retain the exact original-column row hashes and duplicate counts. Views, materialized views, sequences, indexes and catalogs do not masquerade as stored application tables. Legitimate application tables with a `pg_` name prefix remain included. [Relation kinds](https://www.postgresql.org/docs/18/catalog-pg-class.html), [OID privilege functions](https://www.postgresql.org/docs/18/functions-info.html#FUNCTIONS-INFO-ACCESS-TABLE).

Existing table DML checks remain; explicit sequence USAGE/SELECT, schema USAGE and database CONNECT verification supplement the existing prohibition on runtime schema CREATE/migrator membership. Remaining operator catalog reads for target identity, role/database/schema ownership and writer discovery are qualified with `pg_catalog`. The server CLI's backup enumerator and the separate migration-preservation script filter metadata first and generate application queries in a later step; they do not contain the same unsafe name-building predicate. Their row preservation behavior is retained.

## Ubuntu PostgreSQL, firewall and authentication prerequisites

The owner has already corrected these prerequisites. Preserve the verified configuration; the updater does not rewrite PostgreSQL/UFW/HBA settings or restart PostgreSQL/Docker/tunnels. These are initial host setup requirements, not work required before each update.

1. PostgreSQL **18** server/client utilities and `/usr/lib/postgresql/18/bin` must exist. The dedicated TEST database/schema belong to `kindred_test_migrator`. Both dedicated roles use LOGIN, NOSUPERUSER, NOCREATEDB, NOCREATEROLE; runtime has no migrator membership or schema CREATE. The actual `kd.environment_guard` is **test / disposable=false**. Existing private role passwords/session settings remain in `/etc/kindred-dominion/test/*.env`, root-only, never command arguments or Git.
2. PostgreSQL must listen on **127.0.0.1** and **172.23.0.1** (Docker bridge gateway), port **5432**. Preserve other approved local bindings. The `br-kindred` bridge/gateway must exist before PostgreSQL binds that address. Changes to `listen_addresses` require a separately planned PostgreSQL restart; HBA-only changes need reload. Routine updates perform neither.
3. Docker's existing external **kindred-dominion-net**, subnet **172.23.0.0/24**, bridge **br-kindred**, must match the private Compose override. Backend/maintenance `host.docker.internal:host-gateway` must resolve to the host gateway. No database port is published through Compose.
4. Permit only the dedicated bridge source/subnet to the host PostgreSQL listener. A matching UFW initial-setup rule is:

```bash
sudo ufw allow in on br-kindred from 172.23.0.0/24 to 172.23.0.1 port 5432 proto tcp
```

Do not replace this with an unrestricted public 5432 rule or alter unrelated application firewall entries.

5. Preserve local peer-authenticated DBA access for `runuser -u postgres -- createdb` through `/var/run/postgresql`. Permit SCRAM authentication for the dedicated roles on TEST and for the **migrator** on exact isolated rehearsal/recovery database names. The host performs dump/restore/verification over 127.0.0.1; maintenance containers migrate/publish the clones through the bridge. Both paths need HBA coverage, and first-match ordering matters. Example PostgreSQL 18 entries (merge with existing reviewed rules, before applicable rejects):

```text
local all postgres peer
host kindred_dominion_test kindred_test_migrator 127.0.0.1/32 scram-sha-256
host kindred_dominion_test kindred_test_runtime 127.0.0.1/32 scram-sha-256
host /^kd_(rehearsal|recovery)_[0-9a-f]{20}$ kindred_test_migrator 127.0.0.1/32 scram-sha-256
host kindred_dominion_test kindred_test_migrator 172.23.0.0/24 scram-sha-256
host kindred_dominion_test kindred_test_runtime 172.23.0.0/24 scram-sha-256
host /^kd_(rehearsal|recovery)_[0-9a-f]{20}$ kindred_test_migrator 172.23.0.0/24 scram-sha-256
```

The leading slash denotes a PostgreSQL database-name regular expression, not a filesystem path. Runtime access to arbitrary rehearsal databases is not required by the host updater. Do not authorize `all` databases/users or switch to trust authentication. [PostgreSQL HBA syntax, regular expressions and rule order](https://www.postgresql.org/docs/18/auth-pg-hba-conf.html).

Read-only initial setup diagnostics include `ip address show br-kindred`, `sudo ss -lntp 'sport = :5432'`, `sudo ufw status numbered`, and these local DBA queries:

```bash

sudo -u postgres psql -X -d postgres -c 'SELECT line_number,error FROM pg_catalog.pg_hba_file_rules WHERE error IS NOT NULL;'
```

Keep passwords out of diagnostic commands/output. The running backend's connectivity plus the updater's real restored-copy maintenance checks prove the two relevant paths.
