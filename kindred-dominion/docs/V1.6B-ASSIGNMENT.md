# Kindred Dominion — V1.6B
## Complete Player Battle Deck Builder and Battle Selection

Repository: `Revty79/kindereddominion`

Implement a polished, complete battle deck construction experience using the existing persistent player collection and deck systems.

## 1. Prerequisites

Inspect current collection, deck editing, saved deck validation and battle setup functionality.

Reuse functioning implementation rather than creating competing deck systems.

Integrate with V1.5 economy ownership, acquisition and trading services.

Integrate with V1.6A starter collection definitions without requiring final owner approval of individual starter card selections to develop the general deck builder.

Preserve all existing saved decks.

## 2. Collection versus deck separation

Clearly distinguish:

- The player's complete owned collection.
- Individual owned card quantities.
- Recommended starter decks.
- Custom battle decks.
- Incomplete draft decks.
- The currently selected battle deck.

A standard battle deck contains exactly 15 cards.

Card ownership remains quantity-based.

Owning two copies permits including two copies in a deck only when existing gameplay rules allow it.

The same owned copies may be referenced by multiple saved decks.

Creating a deck must not consume or permanently reserve collection assets.

## 3. Complete deck management

Players must be able to:

- Create a new empty deck.
- Create a deck from a recommended starter configuration.
- Rename decks.
- Duplicate decks.
- Edit existing decks.
- Delete decks with confirmation.
- Save incomplete decks as drafts.
- Select the active battle deck.
- Repair invalid decks.

Provide persistent server-authoritative storage.

Do not lose draft changes merely because the player leaves the page or temporarily disconnects.

Provide clear saved, unsaved and saving states.

Use appropriate concurrency protection for multiple browser sessions.

## 4. Deck builder interface

Create a responsive deck editing interface with two clearly distinguishable areas:

- Available collection cards.
- Cards currently selected for the deck.

Display:

- Card artwork.
- Creature name.
- Permanent card ID.
- Kindred.
- Rarity, where configured.
- Placement requirement.
- Existing power and abilities.
- Total owned copies.
- Copies currently selected.
- Remaining copies available for that deck.
- Applicable copy restrictions.

Allow adding and removing individual card copies.

Support repeated cards naturally rather than treating every card identity as selectable only once.

Prevent accidental addition beyond owned quantities or configured copy limits.

Provide a prominent selected-card counter such as 12/15.

Allow card detail inspection without leaving the editing context.

## 5. Search, filtering and sorting

Support collection search and useful filters, including:

- Card name.
- Permanent card ID.
- Kindred.
- Collection.
- Rarity.
- Placement requirement.
- Power.
- Ability category.
- Evolution eligibility.
- Owned cards.
- Cards available for addition.

Support sorting by relevant card characteristics.

Do not hide valid owned cards because they are outside the player's original starting Kindred unless an explicitly selected deck format prohibits them.

Use existing cross-Kindred deck rules.

## 6. Deck analysis

Provide a useful deck composition summary.

Include:

- Total selected cards.
- Unique card identities.
- Additional copies.
- Placement requirement distribution.
- Kindred distribution.
- Evolution cards and supported predecessor cards.
- Relevant ability categories.
- Current legality.

Provide informative warnings for potentially difficult deck compositions, including excessive high-requirement cards or missing evolution prerequisites where appropriate.

Distinguish strategic warnings from actual rule violations.

Do not prevent a legal unconventional deck merely because it is not recommended.

## 7. Validation

Use the authoritative existing game and ownership rules.

Validate:

- Deck size.
- Owned quantities.
- Existing card copy limits.
- Published card eligibility.
- Game-mode restrictions.
- Collection restrictions.
- Competitive format eligibility where configured.
- Card-specific restrictions.

Allow invalid or incomplete decks to remain saved as drafts.

Prevent invalid decks from starting a match.

Explain exactly why a deck is invalid.

Do not silently replace, remove or substitute cards.

## 8. Battle setup integration

Before entering a match, players must be able to select an eligible saved deck.

Display:

- Deck name.
- Kindred composition.
- Card count.
- Legality.
- Selected opponent.
- Existing difficulty and game-mode options.

Remember the player's last selected deck where appropriate.

Revalidate the selected deck on the server before match creation.

Use an authoritative match-start deck snapshot.

Subsequent edits, purchases or trades must not alter an active match's deck.

Preserve existing match-resume functionality.

## 9. Trading and collection integration

When ownership changes:

- Refresh available card quantities.
- Revalidate affected saved decks.
- Identify missing quantities.
- Preserve saved deck contents.
- Explain how the player can repair affected decks.

Do not silently remove cards following a trade, administrative restriction or commercial reversal.

Do not affect an already-started match.

## 10. Interface requirements

Preserve the existing full-bleed card renderer.

Use artwork-first collection cards where appropriate.

Keep deck editing usable on:

- Desktop computers.
- Laptops.
- Tablets.
- Mobile browsers.

Provide appropriate scrolling inside collection and deck-management areas.

The gameplay viewport's no-primary-scroll requirement does not prohibit normal scrolling in the deck builder.

Support keyboard navigation and touchscreen interaction.

Avoid excessive rendering work for large future collections.
