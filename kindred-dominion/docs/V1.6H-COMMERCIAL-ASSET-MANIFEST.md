# Commercial cosmetic asset requirements

V1.6H.5–6 implements ownership, equipment and rendering. **Official commercial artwork is still owner supplied and unapproved.** The latest administrator proposal contains disabled drafts, not an active shop publication. Geometric automated-test fixtures stay under ignored `.local/` paths; they are not official illustrations or a commercial catalog.

## Required owner artwork

| Kindred | Standard card-back cosmetic ID | Standard battlefield cosmetic ID | Working battlefield name |
| --- | --- | --- | --- |
| Nature | `standard-back-nature` | `standard-battlefield-nature` | Ancient Woodland |
| Mythical | `standard-back-mythical` | `standard-battlefield-mythical` | Dragon's Sanctum |
| Arcane | `standard-back-arcane` | `standard-battlefield-arcane` | Astral Nexus |
| Undead | `standard-back-undead` | `standard-battlefield-undead` | Forgotten Crypt |
| Constructs | `standard-back-constructs` | `standard-battlefield-constructs` | The Great Foundry |

Ten images are required to activate the five-Kindred free appearance policy. New players receive only their **original** starting Kindred's standard pair. Until the complete assignment and exact asset revisions are approved, use the neutral card back and board; no placeholder is automatically granted or sold. Optional premium backs and battlefields use separate cosmetic IDs.

Alternate artwork is optional and commissioned per permanent card identity. There are five disabled example variants in the proposal; this is not a requirement to replace all 150 founding illustrations. Specify the card ID, variant name, theme, rights/credit, intended bundle and approval decision for every new variant. Real evolution-chain bundles must use the actual published prerequisites, not an inferred sequence. An alternate license grants no playable copy.

The three implemented treatments (`metallic`, `holographic`, `edge`) need **no image files**. They use static, narrow CSS borders. Their draft prices and publication still need owner review. Asset-based frames, animated artwork/treatments, evolution/victory effects, emblems, portraits, titles and themes remain unsupported, unpublished and unsellable.

## Image specifications

| Asset | Aspect / recommended runtime size | Recommended master | Runtime destination |
| --- | --- | --- | --- |
| Creature alternate illustration | 3:4, 768 × 1024; 1024 × 1365 is within ratio tolerance | Original high-resolution 3:4 raster, ideally 3072 × 4096 within import bounds | `public/assets/cards/<kindred>/` |
| Card back | 3:4, 768 × 1024 | Original 1536 × 2048 or larger 3:4 | `public/assets/card-backs/` |
| Battlefield | 16:9, 1600 × 900; 1920 × 1080 optional | Original landscape 3200 × 1800 | `public/assets/battlefields/` |
| Product cover / announcement | Approximately 1.15:1 crop stage; 1024 pixels wide | Original approximately 2048 pixels wide | Matching registry category, usually `branding/store/` |

Recommendations are production targets. Active portrait assets enforce 3:4 ±0.01; battlefields enforce 16:9 ±0.04. Cosmetic runtime files must be at most 4096 pixels on either axis and 4 MiB each. Aim below 250 KiB for a card/back and 500 KiB for a battlefield on mobile. Keep the original master even when optimization changes format or dimensions. Existing import safety limits remain 10 MB/40 million pixels for local Studio images and the documented package bounds in [the publication contract](V1.2-ARTWORK.md).

Prefer optimized **WebP** for raster production assets; PNG, JPEG and allowlisted geometric SVG are supported. SVG is sanitized before use; scripts, event handlers, external resources, embedded raster data and unsafe SVG features fail validation. Import validates file signature, extension/media consistency, decoded pixels and dimensions, checksums and safe paths. A file extension alone is insufficient.

Artwork contains illustration only. Keep names, IDs, rank, power, ability text, territory diagrams, rarity and pricing out of images. Full-bleed creature art stays 3:4, with faces and focal details clear of existing information overlays. Card backs must not encode card identity, rarity, order or deck composition. Fields need a quiet, crop-safe center and restrained contrast beneath the unchanged 15 tiles, tokens, effects and scores. The runtime dims battlefield art; it never moves board geometry. Review at 1280 × 720, 1366 × 768, larger desktop, 390 × 844 portrait and 844 × 390 landscape, including reduced motion and neutral-board mode.

## Stable identity and immutable files

Use lowercase ASCII IDs and filenames with hyphens, digits and portable relative paths. Example identities:

```json
{
  "id": "red-fox-woodland-dawn",
  "type": "alternate_art",
  "cardId": "n003",
  "asset": { "id": "art-n003-woodland-dawn", "revision": "<generated-sha256-prefix>" },
  "status": "draft",
  "enabled": false
}
```

This is a field excerpt, not a complete publishable definition. Source masters live separately under `artwork-source/cards/nature/`, `artwork-source/card-backs/` or `artwork-source/battlefields/`. The registry records source path/checksum/format/size as well as runtime path/checksum/dimensions/approval. Runtime paths include the generated revision. Never embed base64, a drive path or an external image URL in a card or shop definition.

An artwork update creates a new asset revision and a new shop configuration publication. It does not change the card or cosmetic ID. A cosmetic ID cannot be reassigned to a different card/type. Keep previously published source/runtime revisions for historical receipts and match appearance snapshots. Archival ends new sales without confiscating existing licenses. Refund/dispute restrictions still govern current equipment; an owner's historical match can render its captured artwork revision.

## Publication, activation and backup

1. Import experimental sources through Studio and keep a complete Studio backup. Review art, rights, crops and accessibility before explicitly approving it. The current Studio creature editor is not a standalone battlefield/card-back authoring tool; those images join the **same reviewed publication package contract** as additional category assets, without replacing creature artwork or changing gameplay definitions.
2. Export a reviewed `.kindred.zip` with executable card definitions, additional `content.assets`/`assets.json` entries, original masters, optimized files and complete file checksums. Use a new content publication ID and preserve all founding IDs/mechanics. A package carrying extra cosmetics need not become the active gameplay content version.
3. From the application directory validate and import:

   ```powershell
   node scripts/import-content.mjs "C:\path\reviewed-cosmetics.kindred.zip" --validate-only
   node scripts/import-content.mjs "C:\path\reviewed-cosmetics.kindred.zip"
   npm run validate:assets
   npm run build:player
   npm run build:control
   ```

4. Inspect and stage the corresponding `public/assets`, `artwork-source` and `src/content/published` files together. Run `node scripts/validate-assets.mjs --tracked` and `node scripts/verify-build.mjs dist-player --player --tracked`. The build includes **all production-approved registry assets**, even cosmetic files not referenced by the currently selected creature cards. It excludes testing assets from the public player package and excludes source masters. The protected control package supplies the authenticated hosted artwork service. No artwork database migration or external image host is required after a Git pull.
5. In Administration → Shop, load the latest DEV proposal or edit a private draft. Set exact immutable asset references, names/themes and reviewed prices. Use implemented types only. Save, validate and explicitly publish through the existing configuration editor. Publishing a draft does not happen automatically with deployment. Existing selected configurations are not reseeded.
6. For free starting appearances, review all five assignments, use **Calculate starting appearance review digest**, and record `{digest, reference}` in `startingCosmetics.approval` after owner approval of those exact revisions. Enable new-player grants and optionally backfill, then validate/publish. Changing an assigned image revision invalidates the digest. Production activation remains separately prohibited. Temporary test art cannot activate on hosted TEST.
7. Existing eligible players can claim the approved pair from My artwork. Administrators can preview a player's exact pending grants, enter a reason and apply that reviewed preview. Repeated/concurrent operations do not duplicate grants or overwrite saved choices. Already-owned paid licenses retain their original provenance; the free entitlement is not relabeled as a purchase or a new card grant.
8. Back up committed assets/source masters, configuration publication history and the player database together with the established verified source/database backup process. A portable repository export can be produced with `node scripts/export-content.mjs <publication-id> .local\cosmetics.kindred.zip`; validate it before independent storage. Use the existing split exporter for packages exceeding the single-package bound.

Restoration: restore the matching source bundle/Git revision and verify asset checksums, restore a database backup **into isolation first**, run migration/preservation verification, and inspect archived appearances before any operator recovery. Never overwrite an old asset revision or roll back player ownership merely to repair an image. Repair a missing file from its exact committed source or publish an additive corrected revision. Keep experimental browser-local artwork backups separate; browser storage is never the only copy of official assets.

## Runtime and mobile behavior

Gallery pages fetch at most 24 definitions; images use native lazy loading/async decoding. Card art keeps the shared full-bleed renderer. Backs/fields use authenticated relative image endpoints and immutable registry references, with neutral fallbacks after load failure. Unsupported future cosmetics never appear as purchasable gallery items. Opponent concealed-hand presentation always uses a neutral representative back without hidden card metadata.

CSS treatments use no looping animation, flashing, filters or full-face compositing. Reduced motion is respected. Players can force the neutral battlefield in saved presentation settings; standardized-art formats suppress all cosmetic presentation while retaining ownership. Match appearance snapshots do not rewrite game state, deck snapshots or rules.

Future mobile packaging can reuse the approved static asset output and authenticated appearance service; no Android/iOS project is added here. Source masters stay outside mobile/browser runtime packages. Test actual devices and owner visual acceptance after final art is available.

These are **unpublished planning examples**, not new founding cards or approved commercial policies. Use the existing collection, pool, bundle, booster, rarity and competitive-format tools. Register/publish actual gameplay definitions separately before publishing a shop that references them; unknown identities fail validation even if an experimental product is disabled.

## H.7-8 publication and backup acceptance

Structured Shop administration can assign an immutable product-art ID/revision, change a draft cosmetic's card/Kindred/theme metadata, create a licensed product, configure its exact pool/quantities and preview the result before publication. Published identity relationships remain immutable. Selecting an old configuration for rollback now invokes the same current publication validator; a historical reference to corrupt or missing artwork cannot bypass validation. An actual PostgreSQL regression corrupts a private fixture, confirms rollback is refused atomically and restores the bytes. Existing settled snapshots are retained.

No new final artwork was generated or approved in H.7-8. Test SVGs and their original sources live only in ignored `.local/v1.6h78/*-assets` roots, with temporary testing or explicitly synthetic ordinary-player approval records. They are excluded from official assets, production builds, source control and mobile packages. Published official artwork remains reproducible from Git with 153 validated registry entries and 152 runtime player checksums. Existing source masters are preserved and excluded from the player bundle.

Continue the existing portable import/approval workflow above. Back up the database and the associated committed source revision/immutable asset registry together; retain original masters and archived revisions. Do not delete an old image because a current product no longer selects it. Restore into an isolated database, verify dump/asset checksums, migration ledgers, content/Studio/match validation and ownership reconciliation before considering recovery. H.7-8 restored representative V1.5 data (107 original relations / 566,098 rows) and current V1.6 data (115 relations / 16,289 rows), preserving every existing row/column hash. Private test fixture roots are retained beside their ignored evidence and are not a substitute for official backups. See [owner recovery checklist](V1.6H-OWNER-ACCEPTANCE.md).
