November 27, 2026. Assignment: [Complete Player Battle Deck Builder and Battle Selection](V1.6B-ASSIGNMENT.md). Parent revision: `f5baaebcbe5a5b64cfc2a886de2d198f43d45f5e`.

## Implementation

The existing permanent deck/collection APIs, optimistic deck revisions, ownership ledgers, format publication and authoritative match snapshots are retained. The player builder now supports empty and recommended-template creation; legal duplicate copies; mixed Kindreds; renaming; duplication; confirmed deletion; incomplete/invalid drafts; active battle selection; repair; account-scoped interrupted-edit recovery; filtering; composition analysis; and desktop/touch layouts.

Working edits are separate from the last explicitly saved deck. Autosave cannot silently replace a ready battle deck. Explicit **Save deck** validates and publishes the reviewed list; **Save draft** preserves repair intentions without granting cards or permission to play. Conflicts preserve local edits and the current server copy, with an explicit separate-draft recovery path.

V1.6A configuration approval is not a prerequisite. Inactive starter proposals remain inactive and do not replace official recommendations. Templates do not grant copies. Activated starter configurations can provide their versioned recommended/alternative lists. No original gameplay statistics, permanent IDs, evolution relationships, ownership history or artwork files were changed.

## Migration and preservation

One additive migration: **`1797400000000_deck_workspaces.cjs`**, schema **21 → 22**.

Canonical SHA-256: `a335a89af5331bafc6713358a6909870cdcdedcb8c86811e122380c5dd32124c`.

- Adds a composite deck/owner unique constraint and `kd.deck_workspace`, linked to that exact owner/deck pair.
- Stores bounded working documents, the saved-deck base revision, a working revision and update time. No new ownership or competing deck/inventory system is introduced.
- A discard uses a JSON-null revision tombstone. It hides the discarded working document while retaining the counter, preventing discard/recreate revision reuse.
- Explicit deck publication/history updates and working-copy consumption occur in one existing player-locked transaction. Failed validation or transactions leave prior saved decks and working copies intact.
- Migration creates no working copies, grants, activation flags or replacement decks. Destructive rollback is refused; use an additive correction.

## Integrity and concurrency

Collection copies can be referenced by multiple saved decks. Tests verify that creating, saving and duplicating decks neither changes inventory quantities nor creates inventory reservations.

Server checks retain exact size, actual owned quantities, card-specific and game-mode limits, published/retired identity eligibility, explicit Kindred restrictions and competitive format rules. Incomplete or invalid drafts remain nonplayable and cannot become the active ordinary battle deck. Registered missing/unowned identities remain visible for repair. No card is silently removed or substituted.

Two independent revision checks protect the saved deck and working edits. A second session with a different stale document receives a conflict. An exact working-save retry after an interrupted response can acknowledge the already-stored document without duplicating an operation. Older clients cannot overwrite active unseen working edits. The saved-deck/battle-settings handoff waits for the current revision and avoids resetting already-current options during a background refresh; the existing compiled shop journey covers an immediate save-to-battle transition. Ordinary deck-name updates that omit `formatId` preserve their previous competitive selection.

An actual PostgreSQL regression reproduced a discard/recreate overwrite: the original implementation reused working revision 1 and accepted a stale edit. The revision tombstone correction makes the stale request fail while preserving the newer document. This is covered by the final integration suite and compiled discard journey.

Actual trade settlement transferred the duplicate copies needed by a saved deck. Subsequent validation reported the precise deficit, retained the original list, rejected a new match and permitted explicit repair. A previously started match remained byte-for-byte unchanged. Separate tests cover later edits and acquisitions, stale reviewed revisions, foreign-account access, invalid formats and unauthorized testing escalation.

## Reproduction and limits

From `kindred-dominion`, after `npm ci`:

```powershell
npm run typecheck
npm.cmd run test -- --maxWorkers=1
npm run backend:build
# Privately set KINDRED_ENV_FILE to a verified registered disposable PostgreSQL target.
npm run test:database
npm run validate:assets
npm run build
npm run build:player
npm run build:control
npm run validate:backend-isolation
```

Compiled builder acceptance is `server/tests/browser/deck-builder.spec.ts`, explicitly enabled with `KINDRED_DECK_BUILDER_ACCEPT=yes`. It requires migrated/seeded isolated PostgreSQL, dedicated free API/frontend ports, local synthetic registration, economy enabled, commerce disabled and testing sampler disabled. Tests start/stop their own compiled services. The existing `scripts/validate-economy-browser.mts` runs the eight separately namespaced regression journeys; commerce simulation requires its explicit isolated simulation setting.

Working edits are bounded fifteen-slot documents, not an arbitrary collection dump. Drafts can retain known invalid identities; arbitrary unknown permanent identities cannot enter stored deck slots. Offline recovery requires an already available application and device storage; there is no installable offline shell. Conflicts require explicit review or a separate draft, rather than automatic merging. Full card definitions still follow the existing catalog architecture; the builder bounds rendered cards and lazy-loads illustrations.

Remaining owner acceptance is [the local/hosted checklist](V1.6B-OWNER-ACCEPTANCE.md), including human layout/readability testing. No engineering blocker is being substituted with an owner approval gate. V1.6A exact starter selections remain a separate approval boundary. No homeserver deployment, normal DEV migration, live commerce activation or later feature milestone was undertaken.
