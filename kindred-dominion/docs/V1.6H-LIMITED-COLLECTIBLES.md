# Limited collectibles: operator and content guide

This supplement extends H.5-8 and preserves the V1.6A-G gameplay checkpoint. The shipped edition catalog is empty. No actual limited product, tournament prize, redemption code, physical collectible or live sale is activated. All examples used for validation belong to registered disposable databases and private temporary asset roots.

## Model and immutable promises

An edition has a permanent lowercase ID and immutable lifetime maximum, numbering choice, underlying component identities and quantities, ordinary/sandbox cohort, exclusive-gameplay classification and named lifetime reward quotas. A maximum of one is supported. Supported numeric maxima are positive safe integers, through 9,007,199,254,740,991. Subsequent releases need different edition IDs. The maximum applies to that digital edition; independently published ordinary versions of the underlying gameplay/cosmetic identity remain separate. Use a distinct appearance identity and only capped acquisition routes when authoring an appearance intended to be exclusive to a limited release.

Components are gameplay card quantities or cosmetic licenses. Alternate artwork, card backs, battlefields and implemented treatments use the same issuance service as gameplay cards and mixed fixed bundles. Future effects/bundles can be drafted; an unsupported effect cannot be published merely by naming an asset. A cosmetic license alone never grants a playable card.

Published definitions remain in the edition ledger when omitted, suspended or archived in configuration. Server publication and rollback both check every existing immutable promise. Database triggers independently prohibit cap/core changes, decreased issuance, serial/provenance reassignment, instance/history deletion, retired-instance resurrection and original component or publication-reference replacement. Browser form disabling is only a convenience.

Every issued unit has its own digital UUID, immutable ordinal, optional serial, original owner/provenance, original content and artwork publication references, issuance time, current owner/status/restrictions and permanent history. Serials are allocated sequentially under an edition lock when fulfillment commits. A Checkout hold does not promise a chosen serial. Failed transactions allocate nothing; retired serials are never recycled. Unnumbered editions still have distinct digital instances and auditable lifetime issuance.

Gameplay components use backing inventory editions and the existing quantity/acquisition/lot ledgers. Permanent card IDs and printed mechanics are unchanged. Ordinary grant, reward and correction services cannot mint limited backing editions or consume them as anonymous replacement copies. Exclusive new gameplay identities also reject uncapped ordinary grants. Inventory, acquisition, transfer and exact-instance records remain reconcilable.

## Supply accounting

All shop, achievement, promotion, tournament, administrator and future-redemption adapters call the shared reservation/issuance service. Administrator adapters always preserve administrator-bound provenance; choosing a tournament/promotion label does not fabricate earned or purchased provenance.

The public pool equals maximum minus all immutable reward quotas, public lifetime issuance and active public holds. Each reward allocation has its own issued/pending counters and cannot borrow another allocation or the public pool. Per-account limits count original lifetime purchases plus pending purchases across all SKUs of an edition; transfers and refunds do not reset that limit.

Maximum, lifetime issued, currently active, pending, public availability, lifetime reward allocation and sold-out status are distinct. The UI names the lifetime allocation explicitly. Availability has an observation timestamp and is checked again at purchase. Quotes reserve nothing. Wallet debit and issuance commit atomically; a losing buyer is not charged.

Sandbox editions require permanently designated sandbox accounts. Ordinary editions require ordinary accounts. Sandbox assets cannot enter ordinary Trading Hall settlement. The production environment still rejects economy activation and live payments.

## Create and publish an edition

1. Publish the underlying executable gameplay card or supported cosmetic through the existing content/artwork tools. Use immutable approved repository asset IDs/revisions; preserve source artwork and optimized runtime files. This system does not generate or approve illustrations.
2. Open Administration, **Limited editions**, then create a private configuration draft. Add a template with a new portable ID. Select components, positive lifetime maximum, numbering, cohort and optional reserved allocations. Configure methods, windows, account limit, tradeability and eligibility. Cosmetic trading defaults off.
3. Assign product artwork if required. Existing asset validation checks approval, bytes, checksum, MIME and SVG sanitation. Unsupported/unapproved content blocks publication.
4. Use **Validate edition draft without issuing**. Review the preview and exact immutable promise. Save the draft, provide a publication reason and publish through the existing configuration controls. Actual commercial content still requires owner approval.
5. Set a price/currency and use **Create disabled linked Shop draft**. Shop products are the authoritative price source. This creates a private, disabled fixed-content SKU; it does not publish a sale. One sale delivers one edition unit, which can itself contain multiple disclosed components. Every linked SKU shares the edition cap and account limit.
6. In Shop configuration, open the linked draft and review its exact card quantities/cosmetic identities, price, currency, artwork and testing boundary. Publish only after review and authorization. Publication rejects a mismatch between SKU and edition contents or a reassigned permanent SKU binding. Ordinary Gold founding acquisition remains available.
7. To offer sandbox Hosted Checkout, add the approved fixed SKU to a commercial product using the existing sandbox catalog workflow. Run the documented private sandbox connection/catalog commands; live processing remains unsupported. A commercial catalog alone does not grant an instance. Pausing commerce retains any ambiguous provider hold; it does not assume that a lost response means no Checkout was created. Recover the exact original order/provider session within its retained idempotency window, or investigate the provider metadata and verified webhook history. Do not create a replacement order to free that stock. Verified session expiration/cancellation releases an unissued hold.
8. Inspect issuance by edition ID, page through serial inventory, inspect an exact instance/history and run **Reconcile limited ledgers**. Suspend or archive through another reviewed configuration version; issued instances and historical products remain inspectable.

Published immutable fields are locked in the structured editor. Advanced configuration JSON remains subject to the same server validation. New IDs must use lowercase ASCII and be case-consistent. Never edit an applied migration, manually change issuance counters or reuse an edition ID to promise a larger release.

## Rewards and manual issuance

Economy reward bundles support `{ "type": "limited", "id": "edition-id", "allocationId": "reserved-prize", "quantity": 1 }`. Publish the edition and matching reserved allocation before publishing the reward. Original definitions and fulfillment context are pinned; later retries cannot change provenance. Ordinary automatic rewards cannot reference sandbox-only editions.

Finite stock exhaustion records an immutable exhausted outcome without inventing a substitute or rolling back otherwise legitimate match/XP/currency rewards. A temporary suspension/window/cohort issue retains a pending entitlement. My Collection shows recent limited reward outcomes and provides **Retry original collectible reward** for pending grants. Administrators can inspect recent allocation outcomes with edition monitoring. The account can also retry its exact retained entitlement through `POST /api/limited/rewards/:id/retry`; ownership/authentication and rate limiting apply. This cannot create a new reward source. Investigation should resolve permanently unavailable pending rewards explicitly, without silently manufacturing another collectible.

The administrator issuance form accepts an account, authorized method/allocation and reason. It uses one stable award key for retries. **Start a new authorized award** is an explicit new intention; do not use it to retry an uncertain network response. All grants share stock and quota locks, and are audited and account-bound. There is no public self-grant, arbitrary currency/card grant or NFC redemption endpoint.

## Player collection and trades

My Collection has a direct **View limited collectibles** jump. The paginated gallery filters edition, serial, Kindred, collection, type and configured tradeability. Each exact instance has an unobscuring limited badge, the shared full-bleed portrait card or original cosmetic artwork, provenance, eligibility and history. Images load lazily; unavailable imagery uses the existing fallback. Archived/retired records remain visible. Ordinary gameplay quantities include owned limited gameplay components; decks continue to use permanent card IDs, not serial numbers.

Ordinary quantity trades exclude limited backing lots. The existing direct-offer composer accepts exact offered/requested digital UUIDs and resolves their edition names, serials and fixed contents before consent. Counteroffers, private drafts, acceptance, cancellation, expiration, restrictions, notifications and history retain their existing versioned architecture. Both sides must exchange something; mixed ordinary-card/exact-instance offers are supported. Requested UUIDs are supplied by the other player; the API does not reveal their private collection or purchase history.

An exact instance hold protects the named UUID. Acceptance rechecks its original owner, source ancestry, financial/admin restrictions, edition flags, configured holds and participant eligibility. No equivalent copy or different serial can be substituted. Settlement changes both sides and records component lot transfers, exact instance ownership and immutable serial history in one transaction. Failures roll back both sides. Existing age, level, legitimate-match, account, block, rate and size limits remain. Cosmetic trading needs explicit edition tradeability and cosmetic-trading flags; an originally bound acquisition stays bound.

There are no cash terms, auctions, withdrawals or real-money player transfers. Ordinary readable variants inherit underlying gameplay eligibility. Only separately published, non-founding exclusive gameplay identities can use edition-specific deck formats. Their eligible owned quantities are checked by deck and match services. Founders restrictions and frozen match snapshots remain authoritative; scarcity and serials never modify combat statistics.

## Proposed retirement/refund policy: owner review required

The implemented conservative policy permanently consumes lifetime supply on retirement, refund reversal, revocation or surrender. The exact original instance and serial become terminal; historical issuance stays unchanged and active ownership decreases. This policy needs owner commercial approval before actual limited products launch.

Financial risk creates source-specific holds on exact instances, including cosmetic-only collectibles and assets bought using traced commercial currency. A refund/dispute never automatically confiscates a replacement or another player's instance. Existing explicit financial review chooses to retain original assets or, for an eligible confirmed full fixed-product refund, retire the available originals. Partial fixed-product refunds require case investigation. Ordinary wallet compensation returns the original currency provenance while retiring the exact collectible.

A won dispute or failed pending refund can release its financial hold through existing review without clearing an independent administrator restriction. Once an explicit reversal permanently retires a limited instance, a later failed/cancelled refund cannot automatically resurrect it or mint another serial: the restoration API returns `limited_retirement_terminal` for investigation. Ordinary non-limited restoration continues unchanged. Resolve that financial case explicitly; do not reset cap counters, issue an uncapped backing card or seize a substitute.

## Backup, restoration and future physical identities

Full PostgreSQL backups include edition/configuration versions, reservations, original instances/components, rewards/outcomes, financial holds, exact trade versions/history and all existing ownership/currency ledgers. Retain the verified dump, source bundle, immutable artwork manifest and files, original artwork masters, deployment receipt and private configuration. Never rely on browser storage or external image hosting as the only copy.

Use `sudo kindred-backup` and the existing separate-database restoration/rehearsal workflow. Inspect `sudo kindred-status` on failure. Routine eligible TEST updates remain **`sudo kindred-update`**, with automatic exact-commit CI selection, self-update, backup, isolated restore/migration rehearsal, data verification and health checks. No manual SHA, GitHub approval or operator reinstall is introduced. Production restrictions remain. Never overwrite a newer player database with an older dump or force older images past a schema/recovery safeguard.

Five forward-only additive migrations (25-29) introduce the ledger, configuration/reward integration, history guards and separate cosmetic projection references. Original acquisition provenance remains immutable when a limited projection gains an independent ordinary license. Conversely, a retained revoked ordinary record does not prevent a later limited license from being used. Ownership views and shop eligibility recognize the union of active rights, while original revocation/acquisition records remain unchanged. Existing rows receive only conservative false/null defaults; no historical awards, payments, serials or licenses are fabricated.

For local owner playtesting, first inspect the intended target and make a backup. The implementation session did not migrate the ordinary owner DEV database:

```powershell
cd D:/kindereddominion/kindred-dominion
$env:KINDRED_ENV_FILE = "server/.env.local"

npm run db:backup

```

The first status command must identify the intended local database before the following mutation commands are used. Keep the ignored credential file private. These local commands are separate from the hosted routine, which remains just `sudo kindred-update`.

`limited_physical_reference` is a reserved mapping of namespace/physical identity to digital edition/instance. The physical identity is distinct from both digital UUID and gameplay card ID. There is no hardware, NFC authentication, physical redemption service or actual physical serial registration in this delivery.
