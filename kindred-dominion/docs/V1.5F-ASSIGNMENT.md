# Kindred Dominion — V1.5F
## Stripe Sandbox Integration and Commercial Transaction Infrastructure

Repository: `Revty79/kindereddominion`

The owner has authorized the complete implementation of commercial payment infrastructure using Stripe's test environment.

Real-money payment activation is explicitly prohibited.

The objective is to establish and test the entire commercial purchase lifecycle before public commercial release.

- Apple App Store purchases.
- Google Play purchases.

Separate commercial orders, payment events and asset fulfillment from provider-specific APIs.

All gameplay assets must continue using the accepted economy and ownership services.

- Stripe test secret key.

- Checkout return URLs.
- Provider product mappings.
- Payment activation controls.

Never commit credentials to the repository.

Do not activate live payments under any circumstances.

If owner-provided sandbox credentials are unavailable, complete implementation using automated provider simulations and document the remaining genuine Stripe sandbox verification steps.

## 6. Stripe Checkout

Use Stripe-hosted Checkout for payment entry.

Do not collect or store raw payment card numbers or security codes.

Implement:

- Server-created checkout sessions.
- Authenticated player association.
- Server-authoritative product and price lookup.
- Immutable commercial order snapshots.
- Currency and amount validation.
- Checkout cancellation handling.
- Checkout success handling.
- Session expiration handling.
- Pending payment states.
- Recoverable order history.

Use USD as the initial commercial modeling currency.

Store monetary amounts as integer minor units.

Do not trust client-submitted prices or fulfillment quantities.

Do not grant assets solely because a player returns to a successful checkout page.

Display an unmistakable test-mode indicator throughout the development purchase experience.

## 7. Verified webhook processing

Implement a secure Stripe webhook endpoint.

Requirements:

- Verify webhook signatures using Stripe's documented verification mechanism.
- Preserve the required raw request body for signature verification.
- Reject invalid signatures.
- Reject live-mode events.
- Persist provider event identifiers.
- Support duplicate event delivery.
- Support out-of-order event delivery.
- Validate payment status.
- Validate payment amount and currency.
- Validate payment-provider account and environment association.
- Verify commercial order association.
- Support safe retries and recovery.
- Maintain auditable event-processing states.

Do not fulfill orders that are merely created, pending, unpaid or otherwise unverified.

Use appropriate Stripe payment and Checkout events for supported payment methods.

Initially restrict payment methods to those that have been fully implemented and tested.

## 8. Commercial order fulfillment

Use the existing economy service to deliver:

- Aether.
- Fixed-content card collections.
- Additional playable copies.
- Booster entitlements.
- Alternate artwork.
- Cosmetic assets.
- Future expansion entitlements.

Commercial fulfillment must be transactional and idempotent.

A payment can be fulfilled only once.

Repeated webhook delivery must not duplicate currency or cards.

If payment verification succeeds but fulfillment fails, retain a recoverable pending-fulfillment state.

Provide a safe reconciliation mechanism.

Every commercial asset grant must reference the originating order and payment event.

Do not allow test purchases to create legitimate commercial assets in production.

## 10. Refunds and disputes

- Full refunds.
- Partial refunds.
- Refund failures.
- Duplicate refund notifications.
- Payment disputes.
- Dispute resolution.
- Administrative investigation.

- Purchased cards remain owned.
- Purchased cards have been traded.
