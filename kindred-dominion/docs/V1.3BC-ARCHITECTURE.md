# V1.3B/C architecture and preservation

The application remains React/TypeScript/Vite with one deterministic rules engine shared by play, previews, AI, sandbox, simulation and replay. No account service, database connection, multiplayer implementation or commercial economy was added.

## Owner content and identity

`src/content/owner-design-input.json` preserves the 150 supplied table rows. `owner.ts` maps each into executable V1.3A definitions and the exact five supplied starting decks, plus five separately labelled mixed development decks. The original source definitions, provisional pack, laboratory, artwork and prior evidence are preserved. The new version ID is `founding-kindreds-owner-v1`; its stable set is `founding-kindreds-001`, with independent expansion `foundation`.

`collectible-registry.json` is the permanent assignment ledger, independent of mutable display names. Entries retain the original name, number, gameplay ID, Kindred, set, expansion and retired flag. Existing assignments must be retained forever; retired numbers remain reserved. Future reviewed releases append new entries/prefixes instead of editing old assignments. A retirement is a format/release decision, not a deletion of historical matches or definitions.

`engine/identity.ts` provides canonical serial parsing, numeric sorting without fixed three-digit truncation and shared competitive identity. Standard copy limits aggregate editions by underlying gameplay ID. A different illustration, edition or display name is not another competitive copy allowance. Editions claiming one gameplay identity must have identical executable rules. Owner definitions use lowercase IDs such as `n001` and uppercase display numbers `N001`.

An identity carries number, underlying gameplay ID, founding set, expansion, edition, gameplay revision and stable artwork ID. Metadata carries rarity and current artwork reference/revision. Save card protects established number/gameplay/set/artwork identities and increments the definition revision for actual executable edits. Duplicate strips collectible identity, producing an unnumbered experimental draft. It never silently allocates an official number. Future expansion allocation requires a reviewed registry update that checks every historical assignment and all retired/reserved numbers.

Definition revisions, edition printings, artwork revisions and content releases are independent. Produce a new content checkpoint/version for balancing or illustration updates. Keep the original Owner Design V1 source as the comparison library. A future public content release can retain all 150 gameplay identities while changing names or explicit definition revisions; it receives its own immutable content-version ID.

## Rules and version boundary

The supplied designs use the existing trigger/effect/condition/target library. Their adjacency is explicitly **orthogonal**; the older laboratory's `adjacent` selector still means eight neighbors. Ordinary triggered abilities default to one activation per event and match. Raven, Mana Moth, Ghoul, Vampire, Repair Golem and other explicitly repeatable designs carry their supplied match caps. U017/U029 share a feeding activation identity so inherited lineage restrictions remain effective.

One blocking requirement needed a small numerical extension: C016 and C020 must test the **actual configurable maximum positive fortification**, not an assumed value of three. `maximumFortification` reads the selected ruleset cap in the existing structured numerical DSL. It is safe in passive calculations and is exposed in Studio's expression selector. No duration system, arbitrary formula, new tactical ruleset or broader mechanics library was introduced.

Owner identities/cap expressions require engine 1.3.1 and content schema 2. Legacy 1.1.0 and advanced 1.3.0 definitions/records remain supported; mismatched records cannot silently use owner-only features. Mixed backups declare the newest required engine. Existing matches retain their immutable library, actions, artwork and signatures. Metadata does not fabricate historical counters for old saves.

## Player presentation

`ui/readability.ts` derives public territory, token, fortification, power, protection, aura, dynamic and lifecycle explanations from actual before/after states. The engine emits observer-only boundaries before private draws and after immediate action effects. These diagnostics do not mutate engine events, RNG or signatures.

Placement previews use the real resolver and an actual recorded boundary snapshot. They stop before private draws or automatic turn transfer, so hidden future identities/results are not displayed. Prevention explanations use recorded protection decisions/events; attempts are not presented as successful changes.

Normal action resolution commits and saves once. The optional presentation reads captured snapshots and public differences; its timer, speed, next-step and skip controls execute no additional game action. AI advancement waits for presentation completion. Paused-frame inspection is read-only, and leaving a match clears presentation state. Player explanations redact draw identities; the detailed development record export is compiled only into Studio-enabled builds.

The battlefield distinguishes printed/effective power, raw row power, awarded row points, Domination counts, card bonuses and final totals. Shape-labelled consequences and influence markers supplement color. Right-hand row summaries remain pinned within the horizontally scrolling field. Detailed logs/calculations are expandable. `collection.ts` filters actual executable mechanics and numerically sorts collectible serials.

Nine owner-only prepared scenarios complement the untouched 30 laboratory scenarios. Their factory is lazy and imported through the development host only. The 150 individual automated cases use separate test-only declared-effect drivers; no driver is added to the owner catalog, starting collections or player build.

## Build separation and assets

The main entry lazily selects `GameHost` for local Studio builds and `PlayerHost` when `VITE_STUDIO=0`. PlayerHost imports a validated virtual content module rather than a Studio workspace. Studio, simulator worker, laboratory and owner-demo factories are absent from the tester dependency graph.

`scripts/player-content.ts` selects the owner baseline or an explicitly chosen committed published owner version. It rejects local artwork, unknown owner identities and any referenced creature art lacking production approval. The build emits only selected registered assets, plus the pre-existing neutral UI fallback/crest. It does not copy the full `public` directory. This prevents Vite's normal public-directory copy from publishing the temporary artwork experiment.

`verify-build.mjs` checks compiled bytes against repository checksums, rejects omitted/unapproved/extra historical artwork, checks Git tracking in a checkout, and rejects Studio/worker/lab/demo chunks or strings in player output. Source masters stay in `artwork-source/`, outside client output. The Docker builder validates source and compiled assets; its source-archive mode omits the impossible Git-index check inside a `.git`-free context. The operator's clean-checkout/Docker script supplies that provenance check before building.

Docker serves only `dist-player` through a digest-pinned unprivileged NGINX image. It contains no PostgreSQL service, credentials, source masters, node_modules, Studio source or administrative endpoints. Host port and revision are explicit inputs; binding defaults to loopback. Actual Docker execution is pending owner validation by explicit instruction. No running server, proxy, firewall or unrelated application was changed.
