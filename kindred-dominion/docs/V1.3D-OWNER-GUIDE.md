# V1.3D owner guide

## Start on this Windows computer

The private file `D:\kindereddominion\kindred-dominion\server\.env.local` has been created and DEV initialized. It is intentionally ignored by Git. Keep passwords out of chat, screenshots and committed files.

1. Double-click **Start Kindred Dominion.cmd** in the application folder.
2. Open **http://127.0.0.1:5173/**. Keep the terminal open.
3. Choose **Player account**. Create your own account, then inspect the five Kindreds before confirming a permanent starter. Nature grants exactly 30 unique cards and its recommended 15-card deck.
4. Under **Saved decks**, create, edit, duplicate or choose a default owned deck. **Matches** starts a server-validated computer game; committed moves save automatically. Reload, return to Matches and Resume. Completed games provide verified statistics and a public replay.
5. Press **Ctrl+C** in the startup terminal to stop both application processes. PostgreSQL remains running.

DEV is configured for local account creation. Synthetic acceptance accounts are separate from your future personal account. No personal account or role was guessed for you. This release does not publish a public server.

The initial game screen remains unrestricted **local practice**. Its cards are test access, not permanent ownership. Existing browser saves remain in the same browser and origin. **Return to local practice** leaves that workspace intact. Database accounts retrieve collections, decks and server matches even in a new browser with empty storage.

## First setup on another Windows development computer

Install Git, Node.js **24+** and PostgreSQL **15+** (18 used for validation). Prepare the dedicated nonsuperuser database/role before migrations; never point these commands at another application's database.

```powershell
cd D:\kindereddominion\kindred-dominion
npm ci
npm run backend:configure
npm run db:status
npm run db:migrate
npm run db:status
npm run db:seed
npm run dev:all
```

`backend:configure` creates `server/.env.local` from the template, generates a session secret and prompts privately for the database password with hidden input. It does not create/reset PostgreSQL roles or databases. Alternatively copy `server/.env.example` manually and edit privately. Authorized DEV values: `127.0.0.1:5432`, database `kindred_dominion_dev`, user `kindred_dev`. The backend refuses a different DEV target. Choose `REGISTRATION_MODE=local` for local signup, `invite` for invitation-only, or `closed`; restart after configuration changes. Never prefix server secrets with `VITE_`.

`db:status` prints non-secret identity and migration status. Inspect it before writing. Migration/seed are explicit commands, never automatic startup side effects. Seeding repeats safely and does not replace an already selected newer release. `npm run dev` starts browser-local practice alone. `dev:all` starts backend 3001 and frontend 5173 on loopback; it refuses conflicting ports rather than killing unrelated software.

## Invitations, roles and account status

For invitation-only signup, run `npm run account:invite`. It prints an ignored private filename containing a single-use code valid for seven days. Share the code privately, never commit it. Default accounts are ordinary players. After creating your account, promote only the intended username:

```powershell
node node_modules/tsx/dist/cli.mjs server/cli.ts role --username=your_username --role=administrator --confirm-user=your_username
node node_modules/tsx/dist/cli.mjs server/cli.ts account-status --username=your_username --status=disabled --confirm-user=your_username
```

Use `developer` for private Studio and self-only development grants; administrators may grant other accounts. Use `player` to remove privileged access. Status changes are audited; disabling revokes sessions without deleting history. These examples have not been performed on your personal account. Username is case-insensitive, 3–32 ASCII letters/numbers/underscore/hyphen. Passwords require 12–128 characters, at most 256 UTF-8 bytes.

There is no email/social/self-service recovery. For an operator reset, put a new strong password in an ignored private file:

```powershell
node node_modules/tsx/dist/cli.mjs server/cli.ts password-reset --username=your_username --confirm-user=your_username --private-file=.local/new-password.private
```

This hashes the password, revokes all sessions and audits atomically. Remove the temporary private file after verification. Passwords/session tokens are never command-line flags.

## Private Studio and local import

In the developer build, authorized developers/admins see **Private developer workspace**. Initialize a separate server workspace from bundled content, or preview the local Studio/file import. Preview shows counts/conflicts; download the original local backup, review replacement, then confirm. Import is idempotent and retains the local source. The previous private server revision is archived. Unpublished cards, scenarios, reports, notes, artwork relationships and local replays remain **untrusted development content**. Import grants no permanent cards or statistics.

Existing backups, checkpoints, simulations and export remain available. Saving a private draft never publishes official content. Experimental images may remain in the validated private workspace, up to 16MB total per request; approved images use the repository pipeline. Production player builds exclude Studio UI; backend role checks apply independently.

## Publish official content and artwork

Follow [artwork publication and recovery](V1.2-ARTWORK.md) for original masters, optimized WebP, sanitized SVG, stable revisions, export/import and Git tracking. Do not automatically approve incoming Ember source masters. Keep art independent of gameplay text/statistics and use permanent collectible IDs.

1. Export/validate a reviewed Studio package; import using `node scripts/import-content.mjs <package> --validate-only`, then without that flag.
2. Review and commit definitions, manifest, approved optimized assets and source masters together. Run `npm run validate:assets` and `node scripts/validate-assets.mjs --tracked`. Non-production test illustrations cannot be activated for ordinary players.
3. Append new identities to `src/content/collectible-registry.json`; never renumber, reuse or unretire one. Gameplay changes require a higher definition revision and new content version ID. Artwork/name-only changes still require a new content version ID.
4. Back up DEV, inspect status, then publish the committed version:

```powershell
node node_modules/tsx/dist/cli.mjs server/cli.ts seed --file=src/content/published/reviewed-version.json --activate
```

Omit `--activate` to synchronize without selecting. Ownership/decks reference permanent identity and survive updates. New matches use the selected release; old matches retain original definitions. Retirement blocks new decks/matches and activation of releases containing retired cards without deleting ownership/replays. Keep all founding 30 available in an active starter release; expansion cards never enlarge the free grant.

## Inspect safely in pgAdmin

Connect to DEV and expand **Schemas → kd → Tables**. Use read-only queries; never manually edit inventory, scores or migration ledgers.

```sql
BEGIN READ ONLY;
SELECT current_database(), current_user, inet_server_port();
SELECT name, sha256 FROM kd.migration_checksum ORDER BY name;
SELECT id, username, display_name, role, status, starting_kindred FROM kd.player;
SELECT player_id, edition_id, quantity FROM kd.inventory;
SELECT id, player_id, name, revision, deleted_at FROM kd.deck;
SELECT id, player_id, status, version_id, engine_version, result FROM kd.match;
SELECT * FROM kd.content_selection;
COMMIT;
```

Do not export password hashes, sessions, invitations or private workspaces into screenshots/issues. The app profile shows persistent player ID. Acquisition/inventory-entry tables hold adjustment history; soft-deleted decks retain history.

## Back up and rehearse restoration

Install matching PostgreSQL client binaries. Windows default: `C:/Program Files/PostgreSQL/18/bin`; override `PG_BIN` privately if different. Backups are private and never committed.

```powershell
npm run db:status
node node_modules/tsx/dist/cli.mjs server/cli.ts backup --with-source
```

The printed output is a custom-format dump. Its `.json` receipt contains checksum, consistent table counts, migration/content versions and asset-manifest hash. `--with-source` also creates/verifies `.dump.bundle`; commit tracked work first. Untracked masters/browser-only drafts are not in the bundle: back them up separately until reviewed and committed. Store dump, receipt, bundle and restricted environment backup together in encrypted offline storage. Database data includes private accounts and drafts.

```powershell
node scripts/pg-isolate.mjs resume
node node_modules/tsx/dist/cli.mjs server/cli.ts restore-test --file=.local/v1.3d/backups/the-selected.dump
```

On a new machine with no isolation manifest use `npm run db:create-test`, then restore. Restore creates a fresh database on the separate recorded loopback instance, never overwriting DEV. It checks archive checksum, table counts, migration hashes, content digests, inventory ledger, workspaces and shared-engine replays. `.local/v1.3d/restore.env` configures an isolated API on 3003 with a new session secret, invalidating copied sessions. To rehearse UI, start a second backend using that env and a frontend on 5178 proxying to3003. Never point the normal launcher at restoration data accidentally. Stop the disposable postmaster with `node scripts/pg-isolate.mjs stop` after testing.

`db:reset-dev` refuses owner DEV/TEST/PROD. It only accepts a manifest-bound disposable integration database with exact confirmation/token, and backs up before dropping its `kd` schema. There is no ordinary reset step.

After migration failure, stop writes, preserve diagnostics and source/backup pair, inspect status, then rehearse a fix/restoration in a new database. Do not edit applied migration files or blindly run down migrations. Verify data/compatibility before a separately authorized cutover.
