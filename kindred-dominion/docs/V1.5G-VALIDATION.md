## Integration architecture and corrections

All currency mutations use the existing transactional wallet/lot services; all collectible mutations use the existing inventory/acquisition services. Origins, lifetime first-copy acquisition, reservations, source ancestry and account sandbox boundaries remain authoritative. Match/reward, shop, trade and commercial operations lock participating players consistently, use immutable request terms and retain transactional receipts. Configuration versions and exact content/artwork references are pinned in settled transactions and matches. Publication/rollback cannot rewrite past terms.

G adds eight actual PostgreSQL lifecycle/integration cases. Every founding Kindred starts with exactly 30 bound cards and the approved 15-card starter, acknowledges guide/collection activity, saves a legal deck and completes a normal server match with actual legal actions. The normal three-placement rule remains enforced; only the disposable test clock is aged to avoid waiting thirty wall-clock seconds. Eligible matches grant account XP, participating-Kindred mastery and the configured tutorial reward once, including one five-card guaranteed-new pack. No unrestricted developer match is relabeled as legitimate play.

The purchase/trade race checks simultaneous acquisition of the same identity, shared ownership/available quantity, exact reservation settlement and preservation of an already-created match snapshot. New and returning account histories remain consistent. Existing C tests separately verify win/draw/loss reward branches using validated legal engine replays with explicitly relaxed **fixture-only** participation settings; those are distinguished from full HTTP/GUI matches and do not change default gameplay eligibility.

Confirmed integration defects corrected:

- A delayed progression activity callback could navigate to Collection after the player had already chosen Deck Builder. A navigation generation check now preserves the latest player intent. The compiled shop test deliberately delays that real response and confirms Deck Builder remains selected.
- Commercial administration could display an older load after a later request or confirmed Checkout pause. Request sequencing ignores stale results and a server-confirmed pause is reflected immediately; fresh reconciliation still follows.
- Whole-ledger commercial reporting traced each order separately. On accumulated fixtures this delayed report/pause display. Batched SQL now retains the complete original/restored/compensation-return source closure, including archived holds, with cycle protection and no depth truncation. Actual PostgreSQL compares it against the per-order investigator and checks bounded query count. On 328 accumulated orders, observed reconciliation took 720 ms and source accounting 14 ms; these are development observations, not a hosted performance guarantee.
- Studio simulation completion could appear before the final private report save completed. Completion now waits for durable save; an explicit failed-save state retains results and supports retry/export. The compiled Studio check interrupts the final save, retries it and verifies the retained ten-match report.
- Player packaging rejected every expansion because it required exactly 150 cards. It now preserves all 150 permanent founding identities exactly once while allowing additional validated published identities. Missing, duplicated and reassigned founders remain rejected. Additional cards must also have reviewed active registry assignments; retired/unregistered identities cannot be packaged. The registry test retains exactly 150 founding entries while checking uniqueness across later entries.
- Repository seeding classified every non-default publication as archived, which would permanently block a later official activation. Reviewed fully registered new publications now import as official but remain inactive until explicitly selected. Existing immutable publication channels remain unchanged. A temporary repository tree on actual PostgreSQL exercises seed, unchanged active selection and explicit activation.
- The combined model initially assumed every final pack delivered five cards after a trade reduced the missing-card count. Its conservation assertion caught the error; the model now records actual partial-pack card counts and prorated Gold cost. No game rule was changed.

The broader browser harness initially exceeded the unchanged 600-request/IP/minute guard by running multiple automated multi-player journeys through one loopback identity. Each journey now receives a separate ignored session/rate-key namespace. Existing sessions remain stable within each restart test. Accumulated valid listings also exposed ambiguous test selectors; they now choose the intended counterparty rather than requiring the entire database to contain only one listing. No player data, rate limit or security test was removed.

Primary G changes: `src/content/founding-identities.ts`, player build selection, `PlayerApplication.tsx`, `CommerceAdmin.tsx`, batched commercial source graph/report/reconciliation, integration/browser regressions, deterministic model/runner scripts and delivery documentation. | Administration/publication | Roles and ownership, strict bounded input, audited explicit adjustments, immutable identity/configuration history, draft validation and controlled rollback; settled orders/matches remain pinned |
| Secrets/deployment | Ignored private credentials, sanitized errors/CLI output, no card-payment data in application storage, frontend inheritance/bundle scans, read-only/network-isolated CI, fixed TEST database guard and production deployment prohibition |

No significant confirmed exploit is left unresolved in the tested scope. This is not a formal penetration-test certification. Arranged but otherwise legitimate repeated AI wins, distributed disposable accounts and sophisticated human fraud cannot be perfectly classified by these local rules. Current measured safeguards are retained; speculative risk did not justify banning legitimate trading or changing gameplay. Operational observation and owner-approved policy may tune existing configuration. Test refund/dispute investigation cases intentionally remain retained in disposable history; an investigation queue is not structural ledger corruption.
