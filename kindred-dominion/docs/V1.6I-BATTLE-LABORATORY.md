# V1.6I.6–9 — Battle Laboratory

## Scope and architecture

The existing **Battlefield Sandbox** remains the Studio entry point. Its construction tools, saved scenarios, effective-power inspector, zone ordering, lineage/activation/resurrection counters, evolution stacks, diagnostic state inspection, reset, duplication, computer controls and sandbox-only undo remain available.

Execution opens the same `PersistentGame` component as ordinary account battles. `BattleConnectionContext` supplies either the existing authenticated account transport or an explicit in-memory laboratory transport. The default remains server authority. The laboratory never falls back to account services for unsupported requests.

The shared view includes portrait artwork-first cards, the hand/floating selection and pointer/keyboard/touch controller, immediate legal placement, tile resources, tactical previews, ability/opponent/scoring presentation, Last Move, recorded move replay, inspection and presentation settings. The public projection was extracted from `server/matches.ts` into `src/ui/battle-view.ts`; the server still projects participant zero and conceals the computer's hand and draw order. A developer manual session can project the active participant. This does not add multiplayer networking or weaken production placement validation.

The actual `act`, `createMatch`, legality, scoring, AI, tactical preview and resolution/history functions are reused. Construction `BoardView` remains useful for editing and read-only intermediate diagnostic states; it is not another rules engine. Normal presentation uses bounded capture. **Capture full diagnostics for last action** retains the original complete diagnostic tool by replaying the exact accepted action read-only and checking its signature before exposing its captured states.

## Operator and developer guide

1. Use the existing trusted operator process to give the intended account developer/administrator permission. Studio does not provision administrators through an unauthenticated web endpoint.
2. Sign in and open the protected **Developer Studio**. A fresh private workspace must be initialized explicitly. An existing workspace is opened directly, with no automatic draft replacement.
3. Use **Content Versions and Backups** to download a complete backup before substantial changes. Private source artwork belongs in this recoverable private backup until it is explicitly approved/exported through the existing publishing pipeline.
4. In **Tactical Ruleset Editor**, duplicate a built-in rule or edit an experiment. Save and **Publish private ruleset revision** to obtain an immutable testing revision. This grants no hosted/competitive approval.
5. Open **Battlefield Sandbox**. Choose the rule and current/saved content definitions. **New scenario from ruleset** constructs an empty artificial fixture. Changing definitions/rules explicitly validates dimensions rather than discarding existing cards silently.
6. Alternatively choose both named decks, seed and starting participant, then **Create validated battle from decks**. This calls the unchanged match constructor and deck validator and requires a pinned private rule revision.
7. Set name, description and investigation reference. In artificial construction, edit ownership, tokens, fortification, active player, turn/pass counters, hands/draw order/graveyards/exile, battlefield instances, power, protections and persistent restrictions. Save explicitly.
8. **Execute scenario** opens shared play. Select a card and click/tap or drop on a legal destination. Illegal destinations do not advance the session. **Return to laboratory controls** preserves its current private execution for diagnostics.
9. Manual mode allows either active participant's hand. Computer mode treats Jade as the controlled participant and runs Amber through the existing AI after accepted actions. Existing one-turn/both-computer tools remain; the 200-action experiment ceiling stops an experiment without declaring a result.
10. Use reset to recreate the exact original construction. Save its replay explicitly for the original **Match Replay and Diagnostics** tools. Sandbox undo is a developer control and is not exposed as an ordinary-match undo.

The play surface keeps larger tiles readable through inner battlefield scrolling. The hand and controls remain viewport-bound. Laboratory display preferences stay within that session and use device reduced motion by default; account preferences are unchanged. Closing the play surface releases the underlying Studio controls and restores page scrolling.

## Provenance and repeatability

An artificial fixture may intentionally contain an otherwise unreachable position. Structural validity is required before execution; it must not be described as production-representative merely because it executes.

A production-representative initial scenario must be recreated exactly from two valid decks, seed, starting participant, content and published private rule snapshot. Changing constructed state marks it artificial. This represents engine/deck configuration, not proof of account ownership, competitive eligibility or reward entitlement.

New snapshots record content ID, creation timestamp, engine version and source workspace revision where available, alongside the complete definitions/state. The snapshot is authoritative; a working-draft ID alone is not treated as a unique content revision. Historical scenarios without new metadata remain usable and are labelled legacy artificial/unknown provenance. No historical publication number is invented.

Published rules are pinned by ID, integer revision and complete configuration. The active laboratory copies the definitions, so subsequent input/draft mutations cannot change it. Saved replay records preserve the exact engine, initial state, library, configuration, artwork and optional private rule revision.

## Regression fixtures

Expand **Scenario regression library and automation export**. Select an intended legal action, enter optional expected assertions or explicitly capture the current result, validate/run it and save the construction. Expected assertions support full state signature, score totals and resulting phase. A mismatch reports failure; it is not rewritten to pass automatically.

**Export regression fixture** produces schema 1 `kindred-dominion-scenario-regression`, classified `private-development-only`, containing the scenario's exact content, initial state and metadata. Import validates the package and creates a separate unsaved construction, preserving the existing saved version. Complete Studio/entity exports also remain available.

Run an exported fixture without a browser, database or account service:

```powershell
npx tsx scripts/run-scenario-regression.mts path/to/private-regression.json
```

Success exits 0. A valid fixture whose expected result differs exits 1; malformed or incompatible input also fails. The inherited engine signature detects deterministic divergence; it is not a cryptographic authenticity guarantee. Keep private fixtures and their artwork out of public attachments/repositories unless explicitly approved. The importer rejects unsafe object keys and excessive nesting and caps standalone packages at the private workspace's 16 MiB boundary.

## Isolation and persistence

The in-memory adapter only handles its own match, previews/recent presentation and session display preferences. It has no reward, inventory, trade, issuance, commerce or rating integration. Unknown paths and another session's match identity fail closed. Duplicate operation IDs return the accepted result; changed terms or stale revisions are rejected. Illegal actions do not change the accepted state.

Protected PostgreSQL workspace saves retain same-account authorization, CSRF and optimistic revision checks. Each previous workspace remains in the existing server history. New optional ruleset metadata uses the existing JSON document; no SQL migration or player-data backfill is required. Server and browser stores retain previously published private rule revisions when an older draft/backup is restored and reject attempts to rewrite them.

An application/database restart retains explicitly saved constructions, source artwork, revisions and replay records. Unsaved construction and live execution are session state; save them before leaving or restarting. The existing working-draft and recovery backup processes remain authoritative.
