# Permanent player storage proposal

This is a design for a subsequent server-authoritative stage. No database, account, ownership service, schema migration or live-server connection was created here. The current application is static/browser-local and grants testing access to all 150 cards.

## Ownership and isolation boundaries

| Repository-managed, versioned release content | Future persistent player data |
|---|---|
| Gameplay card identities and definition revisions | Stable player/account identifiers and authentication subjects |
| Rulesets and content-version manifests | Inventory quantities and printing/edition ownership |
| Card art/revisions, backs, icons, battlefields | Saved deck revisions and individual contents |
| Source masters and optimized runtime assets | Server-accepted matches, configurations, events and results |
| Collectible-number registry and classifications | Acquisition history, progression, achievements and rankings |
| Historical release definitions/artwork references | Future tournament/economy records and migration ledger |

Use a dedicated PostgreSQL service/database/volume for Kindred Dominion, separate from Serrian Tide. Suggested logical targets are `kindred_dominion_dev` and `kindred_dominion_prod`; disposable restore targets are separate again. Their credentials, networks, ports, volumes and backup destinations must be distinct. Do not reuse another application's database role, schema, volume or backup directory. A future installation needs its own approval and verified non-secret target check.

Use an owner/migration role separate from the application runtime login. A non-login owner owns the schema; a restricted migrator may assume that owner only in an approved migration job. The runtime role is not a superuser, cannot create databases/roles or apply DDL, and receives only required schema/table/function privileges. Deny public schema creation and cross-database access. Keep inventory/economy mutations behind audited transaction operations; the ordinary client never connects directly to PostgreSQL.

The official PostgreSQL image's `POSTGRES_USER` creates a superuser and must not become the application runtime role. Its initialization scripts run only for an empty data directory, so they are not a migration mechanism. PostgreSQL 18+ also changed its default volume/PGDATA layout; select and pin a supported image/digest at implementation rather than copying old mount examples. See the [official image documentation](https://github.com/docker-library/docs/blob/master/postgres/README.md).

## Proposed data model

| Entity | Keys and intended constraints |
|---|---|
| `player` | Server-generated UUID; public profile separate from private account data; created/disabled timestamps |
| `auth_identity` | Player FK; provider/subject unique; optional professionally implemented password hash, never plaintext |
| `gameplay_card` | Stable UUID plus unique external gameplay ID (`n001`); unique collectible prefix/serial and number; original assignment retained; retired flag, never number reuse |
| `card_set`, `expansion`, `card_membership` | Stable set/expansion IDs independent of display naming; memberships/release state separate from card identity |
| `content_version` | Immutable release ID, engine/schema version, repository commit, manifest SHA-256 and release status |
| `card_definition_revision` | Content-version/card FK; definition revision, immutable canonical rules JSON and copy-limit policy; names can vary by release |
| `artwork_revision` | Stable art ID/revision, portable repository path and checksum; image bytes remain repository/artifact managed |
| `printing` | Card FK, edition/rarity/set/expansion, artwork revision; printings share one underlying gameplay identity |
| `inventory` | `(player_id, printing_id)` unique; integer nonnegative quantity; concurrency/version field if needed |
| `acquisition` | Player FK, unique idempotency key scoped to player/provider, request fingerprint, committed result and timestamps |
| `inventory_ledger` | Immutable signed quantity movements tied to acquisition/adjustment; reversal references instead of deletion |
| `deck` / `deck_revision` | Player FK and immutable revisions referencing content/rules versions and chosen format |
| `deck_card` | Deck revision FK, gameplay/printing references and positive quantities; enforce shared copy caps across all printings |
| `match` / `match_participant` | Stable match ID, server-accepted deck revisions, engine/content/rules versions, seed/configuration and result status |
| `match_event` / `match_snapshot` | Ordered immutable server actions/events and retained exact definitions/results for reconstruction |
| `progression`, `achievement`, `ranking`, `tournament_entry` | Future versioned domain records referencing players/matches; not enabled in this stage |
| `economy_transaction` / `economy_entry` | Future append-only balanced ledger, currency/item identities, external receipt hashes and idempotency; no payment-card details |
| `schema_migration` | Ordered migration ID, checksum, application release, applied timestamp and execution identity |

Prefix and serial are not fixed-width integers capped at 999. Use an exact numeric serial or canonical decimal representation with at least three displayed digits. Formatting must **pad to a minimum of three**, never truncate longer serials. Store prefix and Kindred association in a registry so future Kindreds can add distinct prefixes. Existing assignments cannot be updated to another card; retired rows remain reserved even when nobody owns a copy.

Display names, editions and artwork references are not inventory/copy-limit identities. Alternative images and special editions reference the same `gameplay_card`. A deck's competitive count sums every printing of that card against the copy policy in the accepted rules/content version. Balancing increments definition revisions without changing ownership or collectible numbers.

Official content still originates in committed repository releases. The database retains immutable manifest hashes and the minimal exact rules/definition snapshots required to reconstruct historical matches. Do not let ordinary application writes edit release definitions. Retain the repository commit and referenced artwork revisions with backups so historical content remains retrievable after hosting migration.

## Atomic acquisition and duplication resistance

All acquisition/inventory changes are initiated by the future authenticated server, never by a browser claim:

1. Begin a database transaction and insert an acquisition/idempotency claim with a unique key and canonical request fingerprint.
2. On a duplicate key, return the prior committed response only if the fingerprint matches; otherwise reject the conflicting request.
3. Verify the server-authorized grant/receipt and rule version. Lock affected inventory/account rows in a stable order, or use a serializable transaction with bounded whole-transaction retries.
4. Append ledger movements, atomically increment/decrement inventory, enforce nonnegative quantities and all reference/uniqueness constraints.
5. Persist the complete acquisition response and commit all effects together. A crash cannot commit inventory without its acquisition/ledger record.

PostgreSQL's `ON CONFLICT` supports atomic insert/update behavior, but it does not replace the transaction around the complete acquisition. See [PostgreSQL INSERT](https://www.postgresql.org/docs/18/sql-insert.html). Provider webhooks also need unique provider-event/receipt identities; do not grant twice because delivery was retried. Administrative corrections are separately authorized, attributed ledger adjustments, not arbitrary quantity overwrites.

At match acceptance, the server validates ownership, deck legality, shared copy limits, current format eligibility and exact content version. The server owns hidden hands, RNG, action validation and results. Client previews and local match records are advisory. Current replay signatures detect deterministic divergence; they are not cryptographic proof of ownership or trusted competitive results. Use strong release hashes and server-held authoritative event records in the future service.

## Accounts and sensitive data

Use a maintained authentication implementation/provider in the authorized backend stage. Store provider subjects and, only if password authentication is selected, properly salted modern password hashes. Never store plaintext passwords, payment-card numbers/security codes or browser-provided ownership totals. Payment processing, acquisition products, currencies and paid boosters are not implemented or selected by this proposal.

Keep credentials in host secret management/private environment or PostgreSQL service files outside Git. Restrict file permissions and role scope. Do not print secrets in receipts/logs. Repository ignores cover `.env`, service/password files, dumps and backups; `.env.example` contains only non-secret static deployment examples. Private player data and database backups are never application build assets.

## Migration and update plan

Future migrations are reviewed, ordered and checksummed. Record them in `schema_migration`; never silently edit an applied migration. Use a dedicated migrator and PostgreSQL advisory locking to prevent concurrent migration jobs. Prefer expand/backfill/contract changes that keep the previous compatible application release usable during the rollout window. Destructive changes need separate authorization and a tested restoration route.

Before an approved production migration, verify the target database/user/server version without exposing credentials. Back up, restore independently and exercise reads/constraints before applying to the live target. After applying, inspect the actual target's migration ledger and a read smoke test. A disposable success is not proof the intended live database was migrated. None of these live actions occur in this stage.

Application updates replace immutable images/content; they do not replace or delete the database volume. Rollback uses a schema-compatible previous image. Do not assume a destructive down-migration can reverse committed player acquisitions. If restoration is required, explicitly freeze writers and follow the reviewed recovery plan rather than mixing old/new inventory histories.

## Backup, independent restoration and retention proposal

Set recovery objectives with the owner at backend implementation. A starting proposal is automated nightly custom-format dumps plus pre-migration backups, with 7 daily, 4 weekly and 12 monthly retained generations. Keep an encrypted independent/off-server copy and monitor backup age, checksum, size and command exit status. Scheduling is a future operator configuration in an explicit timezone, not a cron job installed by this stage.

Use a version-compatible client and `pg_dump -Fc` against the verified Kindred database. Record database/server/client versions, migration ledger, content-manifest/commit IDs, dump checksum and capture time. Dumps do not contain all cluster-global role definitions; preserve reviewed role provisioning separately without committing credentials. See [pg_dump](https://www.postgresql.org/docs/18/app-pgdump.html).

Pair player-data backups with an independently retained Git/content archive containing the exact official definitions, asset manifests, original masters and optimized artwork revisions. Keep application images or reproducible pinned build inputs for the accepted engine. Checksums verify the pair; a database dump without its referenced content is incomplete recovery evidence.

At least monthly, and before significant migrations:

1. Restore a selected backup into an isolated disposable Kindred database/volume with no production credentials, routes or writers.
2. Verify checksums, migration ledger, player/card identities, inventory totals, acquisition/ledger reconciliation, nonnegative quantities, foreign keys and uniqueness constraints.
3. Reconstruct representative archived matches against the recorded engine/content and verify artwork references from the retained release archive.
4. Run application read tests and controlled disposable idempotency/concurrency tests. Do not send restored notifications, process real purchases or expose private data.
5. Record source backup, target identity, exact commands/versions, results and recovery time, then destroy only the explicitly verified disposable target after its retention decision.

A successful dump is not a successful restoration test. If nightly dumps cannot meet the chosen recovery-point objective, add WAL archiving/point-in-time recovery in the authorized storage stage. The backup store must remain independent of the primary data volume and host.

## Development, production and later hosting migration

Use separate databases, roles, secrets, networks, volumes and backup destinations for development/production. Never seed development from identifiable production player data by default. Prefer synthetic fixtures; any later sanitized copy requires explicit authorization and verified scrubbing.

For a future host move, provision the new isolated target, restore and rehearse, then freeze/drain old writers, capture the final consistent data/ledger state and switch only after verification. Preserve stable IDs, content versions, artwork hashes and acquisition idempotency keys. Keep the old target read-only during the rollback window. Do not let two active writers independently grant the same acquisition.

Current browser decks may later be imported only as untrusted drafts and revalidated against server rules/inventory. Browser-local ownership/progression does not become authoritative during migration. The existing [artwork publication and restoration process](V1.2-ARTWORK.md) remains the content-side recovery path; the future database plan adds player persistence without replacing that repository-managed content boundary.
