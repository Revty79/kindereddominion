# V1.5A one-command updater correction

Normal operation after the one-time upgrade is **`sudo kindred-update`**. [Installation, release publication and recovery](V1.5-OPERATIONS.md) are the operator instructions. No game mechanics, database migrations, economy features or shared DEV data changed in this correction.

## Release and code trust

Main is not treated as automatically approved. The owner publishes an eligible exact main revision through **Approve Kindred release** after **Validate Kindred source** succeeds. Public HTTPS API verification checks the latest run attempts, fixed repository/owner IDs, required job identities, every job/step outcome and the SHA-256 of both workflow files against root-installed trust. Failed/pending/skipped/spoofed/unapproved evidence fails closed. Missing API access never enables an unsigned or locally acknowledged fallback. Explicit revision selection uses the same approval checks. A newer unapproved main commit can be skipped in favor of the newest approved forward release; the installed approved revision produces a health-checked no-op.

The stable launcher checks root-owned immutable runtime bytes before importing code. Discovery and operator staging hold the deployment lock continuously. Staging reads regular files directly from the approved commit's Git objects, bounds sizes, validates the protocol/file list, compiles Python and runs a separate import check without credentials. Activation is an atomic fsynced pointer update with previous-version and upgrade receipts. Failed imports/partial staging never activate. Approved candidate code handles the subsequent deployment, and prior tooling remains available for operator-only recovery. Application deployment failures retain the new recovery tooling and the existing database-uncertainty journal.

The root policy and stable protocol are separate trust anchors; routine runtime implementation changes self-update without reinstalling. Changing the approval authority, pinned workflows or stable protocol is an explicit owner-reviewed trust rotation. This prevents an unreviewed main commit from weakening its own release gate.

## Recovery usability

Before migration, the working application stays running through discovery, operator validation, builds and tests. A later pre-migration failure resumes only schema-compatible old images. Inspect `sudo kindred-status` and its private log, correct the cause, then retry `sudo kindred-update`.

After any uncertain live migration, the ordinary command explains that intervention is needed and refuses a newer revision. Review status/logs and run **`sudo kindred-update --resume`** to select that exact failed SHA automatically and take a fresh safety backup/rehearsal. Existing separate-database recovery commands retain newer player data; no old dump is automatically restored over TEST.

If active tooling is damaged, **`sudo kindred-update --recover-operator`** verifies and atomically restores the previous operator pointer under the same lock. It never deploys or touches application data. Existing migration uncertainty continues to apply. If the retained bundle is damaged too, the documented reviewed one-time installer is the recovery path.
