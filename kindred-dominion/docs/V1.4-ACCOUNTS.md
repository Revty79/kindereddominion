# V1.4 accounts and local recovery

## Registration and permissions

Open the player application and choose **Begin your collection**, or **Log in → Create an account**. Supply a unique username, valid email address, display name and matching password/confirmation. New passwords require 15–128 characters, at most 256 UTF-8 bytes. Existing shorter passwords still work for login; changing one uses the new policy. Usernames and emails are normalized to lowercase and uniquely constrained in PostgreSQL.

Older accounts retain their identity, password hash, role, collection, decks and history. Their newly added email may be empty; add it under **Settings → Account security** with the current password. Email format/uniqueness are checked, but **email delivery and address verification are not configured**. The application does not claim that an email was sent or that its address was verified.

Every new account starts as `player`. The first registered account receives no special privileges. The operator can promote the intended registered username using the existing audited command:

```powershell
cd D:\kindereddominion\kindred-dominion
node node_modules/tsx/dist/cli.mjs server/cli.ts role --username=YOUR_USERNAME --role=administrator --confirm-user=YOUR_USERNAME
```

Use `developer` for private Studio access and existing self-only development grants, or `player` to remove privileges. The command reads the private backend environment and requires exact username confirmation. No owner username or privileged password is hardcoded or guessed. Refresh/log in again to update navigation. The full development application exposes **Developer Studio** only to developer/admin accounts; the player release omits its implementation. Backend checks apply regardless of navigation or client modifications.

## Password change

Use **Settings → Account security → Change password**. The server checks the current password, applies the same bounded scrypt hashing already in use, updates atomically, revokes all prior sessions/recovery codes and rotates the current session. Other browsers must log in again. CSRF/Origin checks and persistent per-account limits apply.

## Secure local recovery testing

This is an explicitly development-only recovery path, available in DEV and the guarded disposable integration environment. It is not an email service. The operator must independently verify the intended account before issuing a code; knowing a username is not authority to recover someone else's account.

```powershell
node node_modules/tsx/dist/cli.mjs server/cli.ts recovery-code --username=YOUR_USERNAME --confirm-user=YOUR_USERNAME
```

The command prints an ignored private filename under `.local/v1.4/recovery/`, never the code. Open that file privately, choose **Log in → Recover an account**, and enter the username, code and matching new passwords. The code is random, expires after 15 minutes, and can be used once. Issuing another code invalidates previous ones. PostgreSQL stores only a secret-keyed digest. Neither a URL nor a client bundle contains the code. Successful recovery revokes every session/code and requires normal login; it does not automatically authenticate the recovered account. Remove the consumed private file after verification.

Hosted TEST/PROD refuse this code-issuing method and the local recovery endpoint. The existing private operator `password-reset` procedure remains available for assisted recovery with the required hosted-environment acknowledgement. It also revokes sessions and recovery codes. No hosted environment has been accessed or deployed by this assignment.

The recovery constraints follow [OWASP recovery guidance](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html); current-password checks and session rotation follow [OWASP authentication guidance](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html). This remains a locally tested implementation, not an independent security certification; hosted email, MFA, external review and operational monitoring remain separate work.

## Additive migration and verification

`1795725000000_player_identity.cjs` adds nullable normalized email plus a unique index, and the hashed/expiring recovery-code table. Earlier migrations are unchanged. New registration requires email; old accounts are not assigned invented addresses. Migration status and checksums are guarded by the existing tooling.
