# V1.6E — Accepted action presentation

Date: 2026-11-27. Scope: [owner assignment](V1.6E-ASSIGNMENT.md). Builds upon V1.6D commit `fe55a57a442d30beb6f71f90a9d607d1204201c2`.

## Implementation

The persistent action endpoint still validates, resolves, records and settles the player action and computer response in its existing PostgreSQL transaction. The computer still uses the existing deterministic search and shared engine. Animation completion does not call this endpoint, update a match, grant a reward or change a deadline.

Each successful action response additionally contains a versioned `resolution` batch. Stable event identities use the match ID, persisted action sequence and event ordinal. The batch identifies its exact previous/resulting match revisions. Each event includes the actor, publicly revealed played card, representative hand origin, destination, previous/resulting public battlefield and scores, classified tile changes and public ability description when applicable. The ordered events cover turn opening, selection, movement, arrival, actual influence, actual ability activation, effects, scoring and turn transfer. Existing `presentation` review frames remain compatible.

`src/ui/resolution-presentation.ts` constructs events from the **actual accepted resolver observations**, never the speculative preview. Two observer-only arrival checkpoints were added to `game.ts`; they do not modify game state, events, RNG, mechanics or record signatures. All 150 founding definitions produce the same result with and without the observer. V1.6D's effect classifier and symbols are shared between previews and accepted effects.

The public projection explicitly selects battlefield information. Full game states, diagnostic details, seeds/RNG, hidden hand/draw identities, contexts, lineages and private histories are excluded. A played card is revealed only after an observed battlefield arrival establishes its public identity. Hidden-hand indices are never supplied or inferred. Concealed draw/generation triggers do not acquire a public source identity merely because the diagnostic observer can see them. Actual resolved random public effects may be presented; future random outcomes remain absent from previews.

## Player experience

- While the action request is pending, the status communicates server resolution and the opponent decision. No artificial thinking delay is inserted. During accepted playback, the active actor is labeled explicitly.
- The opponent's representative **concealed hand** marker highlights, the single accepted card is revealed using the existing full-bleed portrait renderer, and a transform/opacity animation moves it to the highlighted destination. No remaining hand cards or exact hidden slots are exposed.
- Placement effects illuminate only actually changed tiles. Direction arrows originate at the public influence source. **RESOLVED** badges distinguish accepted effects from V1.6D's **PREVIEW**/**PATTERN** overlays. T/P/F values and CAP/X/SH/EV/R/SAC/REV/RET/EX/A/D symbols share the established visual vocabulary.
- Ability activations precede their actual effect frames. Changes use reusable primitives for power, ownership, tokens, fortification, protection, departure/arrival, evolution, replacement and other supported lifecycle effects. Skipped abilities are not presented as activations; an activated ability with no eligible target can have no numerical change.
- Departing or transforming creatures remain visible during the effect dwell, followed by the authoritative resulting card/empty tile. The accepted sequence is also readable in **Details & log**, with ordered captions and before/after numerical descriptions.
- Score changes retain the previous action-boundary totals and actual resulting totals. Changed scoring rows pulse, with the authoritative resulting score retained. Intermediate battlefield frames come from real snapshots; score calculations are unchanged.
- The same consequence system presents player actions. Player selection/movement events are omitted from automatic playback so V1.6C's accepted placement animation is not repeated.

## Authority, recovery and bounds

`useResolutionPresentation` keeps its visual queue separate from the latest persistent match prop. That prop updates immediately when the accepted response arrives; it is the source for recovery and subsequent server requests. Inputs remain blocked during the queue. Playback advances only visual events and never resubmits actions.

The queue checks match identity, revision continuity, event continuity and the final public position. Repeated deliveries/stale timer callbacks are ignored. Contiguous newer batches can append; gaps, mismatches and missing/truncated streams reconcile immediately. A newer saved revision obtained by background refresh replaces the old visual queue. Restoring or remounting a match displays its latest saved state rather than replaying transient response metadata.

Skip, focus loss, hidden documents, viewport/fullscreen changes, reduced motion and an animation API failure all reconcile to authority. An event timer and total sequence budget prevent an animation from retaining input indefinitely. None affects a server deadline. Authoritative multiplayer networking/timers are not introduced; the event consumer depends on accepted actors/actions, not the computer search implementation, and can be reused by a future network/replay adapter.

Central timings live in `src/player/resolution-queue.ts`: turn 90 ms, selection 180 ms, flight 420 ms, arrival 200 ms, influence 220 ms, ability 280 ms, other effects 300 ms and score 300 ms. The total uninterrupted sequence budget is 6.5 seconds. Skip is available throughout. Full player preference controls remain reserved for V1.6F.

Observer capture stores at most 96 snapshots per action, reduced according to serialized input size, and 384 diagnostic entries. Oversized captures disable optional playback while the real action continues. Public batches are capped at 96 events / 1,500,000 serialized characters; the client queue is capped at 192 events with 32 recent batch identities. An over-budget chain shows the saved result and retains the ordinary battle log. Public effects are event-driven React updates; movement uses the browser animation compositor rather than rerendering the battlefield on every animation frame. No particle system or per-card animation code was introduced.

## Known limits

1. Physical phone/tablet behavior and the owner's preferred pacing/readability require manual acceptance. Desktop Chromium and emulated touch viewports do not establish physical-device approval.
2. Exceptionally long chains reconcile after the bounded presentation budget; the saved result and readable log remain available. All card mechanics still resolve on the server.
3. Presentation metadata is transient. Reloading after a dropped response deliberately shows the saved position; it does not reconstruct a missing animation. Existing verified replay remains available independently.
4. Multiplayer transport, live turn timers, new gameplay, new balance, new card content and V1.6F preferences were not implemented.
5. The new automatic presentation is on persistent player battles. Legacy offline practice keeps its existing presentation controls.

No homeserver connection or deployment was performed. The trusted exact-commit TEST release workflow and `sudo kindred-update` are unchanged.
