# Store product artwork and publication

V1.6H.1–2 uses the existing immutable repository asset registry and publication validator. The storefront is functional while the owner prepares original commercial artwork. No final packaging artwork or new creature illustration is supplied in this milestone.

## Owner artwork checklist

Prepare original covers for general/Kindred/premium/collector boosters, collection and deluxe bundles, artwork collections, customization products, featured collections and Aether packages. Only provide art for products actually approved for publication; future products need no invented inventory or pricing.

Recommended cover delivery is a high-resolution raster master, about 2,048 pixels wide, with important subjects near the center. The current cover stage is approximately 1.15:1 and crops artwork to fill it. Keep creature faces, symbols and essential visual elements away from crop edges. Product names, descriptions, contents, price, currency, schedules and ownership are rendered by the interface and should remain independent of the image. These are presentation recommendations, not new gameplay rules or permanent commercial policies.

The existing pipeline supports WebP, PNG, JPEG and sanitized geometric SVG. Prefer an optimized WebP runtime image and preserve the original source separately. Existing source size/pixel bounds, signature/decoded-image checks, SVG allowlist, checksums, case-consistent paths and approval requirements still apply. Creature artwork retains its original full-bleed 3:4 proportions and permanent card relationship.

## Stable references

Each product may reference an approved image using the existing `artwork` field:

```json
{
  "id": "founding-first",
  "artwork": {
    "id": "store-founding-booster",
    "revision": "<generated-sha256-prefix>"
  },
  "featured": false,
  "edition": "standard"
}
```

This is a field excerpt; keep the product's complete validated definition. Use the exact revision generated by the publication pipeline. Never paste a local path, external image URL or base64 image into a product definition. Product IDs and artwork IDs are independent. Updating a cover creates a new immutable image revision and a new reviewed shop configuration version; it does not change the product/card identity or rewrite historical purchases.

Branding assets can use `public/assets/branding/` and `artwork-source/branding/`, including a store subdirectory where supported by the reviewed package. Existing `card-backs`, `battlefields`, `icons` and other registry categories remain available for their intended assets. Product covers do not require assigning packaging art as a creature illustration.

## Import and approve

Use [the established publication package contract](V1.2-ARTWORK.md). A reviewed `.kindred.zip` must include its source/runtime bytes, matching `content.assets`/`assets.json`, file manifest, checksums and approval level. Preserve the existing executable creature definitions and their artwork references. The importer accepts additional approved registry assets; there is no requirement to replace a card illustration with a product cover. There is no new standalone packaging-art editor in H.1–2.

From the application directory:

```powershell
node scripts/import-content.mjs "C:\path\reviewed-store-art.kindred.zip" --validate-only
node scripts/import-content.mjs "C:\path\reviewed-store-art.kindred.zip"
npm run validate:assets
```

Review the resulting source/runtime files, manifest and publication before committing them together. Preserve older revisions. Publish the product reference through the existing administrator Shop configuration draft, validation and explicit publication workflow. For incoming assets, keep any new content publication inactive unless the owner separately approves it for gameplay; a product cover is not authorization to change the active creature catalog.

Shop publication checks the referenced approved image, bytes, checksum and supported format. The player artwork endpoint authenticates the account, checks the selected shop version and product visibility, enforces sandbox-only boundaries and verifies the immutable asset again. Draft, archived, unauthorized and stale-version cover requests return unavailable. Broken runtime images use a visible fallback; the fallback never grants an item or implies an unapproved product is purchasable.

## Development and recovery

Code-rendered packaging placeholders are labeled **Development packaging preview · official artwork pending**. Individual-card covers identify the existing published creature preview. Acceptance fixtures reuse committed illustrations with names/descriptions identifying their temporary development purpose; those products are confined to registered disposable data and are not shipped as an active store publication.

Keep source masters, optimized images, manifests and corresponding definitions together in Git and source backups. Restore a verified source bundle and the appropriate database/configuration backup using the existing recovery procedures. Do not overwrite immutable image revisions or restore older player balances merely to change a cover. Archived purchase receipts retain their original configuration references and labels after a product is retired.

V1.6H.5–6 adds functional card backs, personal battlefields, static treatments and the artwork gallery. Official images and exact starting-grant approval remain pending. See [the commercial asset specification](V1.6H-COMMERCIAL-ASSET-MANIFEST.md). Supplying an image alone never approves or activates its sale.
